# PROJECT_RULES — постійні правила Taxo

Цей файл є **канонічним джерелом постійних правил проєкту**. Його потрібно читати **перед будь-якою новою роботою з Taxo разом із `PROJECT_STATE.md`**.

- `PROJECT_RULES.md` = правила, які не змінюються від ревізії до ревізії.
- `PROJECT_STATE.md` = поточний стан, останній checkpoint і наступний крок.
- Якщо старий чат, гілка, release note або інший документ суперечить цим двом файлам, пріоритет мають `PROJECT_RULES.md` + актуальний `PROJECT_STATE.md`.

## 1. Версії та ревізії

- Кожен завершений **кодовий** крок, виправлення або переробка отримує нову ревізію.
- Послідовність: `r1 -> r2 -> ... -> r10`.
- Після `r10` автоматично піднімається minor: `10.2-r10 -> 10.3-r1`.
- Перший розряд (`10 -> 11`) змінюється тільки за прямим рішенням власника проєкту.
- Уже видану користувачу ревізію **ніколи не перевикористовувати** для нового тестового стану.
- Після видачі тестового архіву наступна кодова зміна починається вже з наступної ревізії.

## 2. Тестові архіви — без повторних назв

Для кожної нової тестової ревізії має бути нова, читабельна назва.

Приклад для `10.2-r8`:
- ZIP: `Taxo_v10_2_candidate_r8_START.zip`
- коренева папка всередині: `Taxo_v10_2_candidate_r8_START/`

Обов’язково:
- назва ZIP і кореневої папки відповідає поточній ревізії;
- ніяких commit-хешів у назві;
- ніяких `(1)`, `(2)` та подібних дублювань;
- ніякого вкладеного другого ZIP;
- старий архів не видавати повторно як «новий тест»;
- якщо нового архіву ще немає — прямо сказати це, а не давати посилання на попередню ревізію;
- перед тим як дати посилання користувачу, перевірити на GitHub **тег, asset і точну назву файлу**.

## 3. Кожен завершений кодовий крок закінчується тестуванням

Крок не вважається завершеним лише після commit/push.

Потрібно:
1. пройти regression suite;
2. зібрати START-пакет;
3. перевірити пакет;
4. опублікувати candidate/prerelease або artifact згідно з поточним циклом;
5. дати користувачу **пряме посилання на новий тестовий архів**;
6. оновити `PROJECT_STATE.md`.

START-пакет формується для кожної тестової ревізії. Windows/macOS executable-пакети робляться на окремих контрольних точках, а не обов’язково після кожної дрібної ревізії.

## 4. Синхронізація номера версії

Перед видачею тестового пакета однакову версію/ревізію повинні мати:
- `main.APP_VERSION`;
- `VERSION.txt`;
- release notes поточного candidate;
- назва гілки/PR, коли вона використовується для candidate;
- назва START ZIP;
- назва кореневої папки;
- regression-тести, що перевіряють поточну ревізію;
- `PROJECT_STATE.md`.

## 5. Git і checkpoints

- Актуальна робота починається тільки від стану, указаного в `PROJECT_STATE.md`.
- Старі work/candidate/tmp-гілки не використовувати як нову базу без окремого рішення.
- Опубліковані теги та releases не пересувати і не переписувати.
- Stable tag є immutable rollback checkpoint.
- Назви гілок, архівів і папок мають бути читабельними для людини.

## 6. Дані користувача

- Робочі SQLite-БД не входять у GitHub repository/release.
- Скани тахокарт, копії документів, персональні файли, кеші та робочі архіви не входять у кодовий пакет.
- Оновлення програми не повинно вимагати повторного введення робочих даних.
- Історію не видаляти автоматично заради спрощення нової моделі.

## 7. План і факт — різні речі

Це базовий інваріант Taxo:
- маршрут/графік/план = очікувана робота;
- фактична діяльність = те, що реально відбулося;
- факт не можна тихо замінювати планом;
- якщо звіт дозволяє підставити план замість відсутнього факту, програма повинна **явно запитати підтвердження користувача**;
- перепланування змінює план, але не стирає вже внесений факт.

## 8. Бланк підтвердження діяльності

- Бланк підтвердження діяльності є **фактичним документом**, а не похідним від планового маршруту.
- Межі бланка визначаються реальною відсутністю/діяльністю.
- Можливі кілька причин і кілька фактичних інтервалів.
- **Межа бланка не дорівнює автоматично межі робочого часу.**
- Між роботою та відпочинком/відсутністю може існувати ручний проміжок, який не входить ні в бланк, ні в оплачуваний робочий час, але також не є безперервним відпочинком (наприклад добирання до/від транспортного засобу).
- Такий проміжок Taxo **не класифікує автоматично**: не створює для нього новий бланк, не розширює на нього існуючий бланк і не додає його в табель.
- Редагування фактичних меж бланка саме по собі не повинно пересувати `worklog`; фактичні межі роботи змінюються лише окремою явною дією/фактичним джерелом.
- Реальні відхилення — раннє/пізнє повернення, затримка біля авто, несправність, лікарняний посеред зміни, добирання до/від ТЗ тощо — мають зберігати різницю між планом, роботою, відпочинком і некласифікованим ручним часом.

## 9. Роль водія та історія

- Роль «Водій» має датовані періоди дії.
- Історично помилкове автоматичне призначення ролі не повинно породжувати нові години у табелі.
- Виправлення ролі не дорівнює звільненню.
- Старі записи не видаляються автоматично; їхній вплив на розрахунки контролюється правилами чинності ролі.

## 10. Робочий час

- `planned_hours` — оплачуваний план, а не просто різниця між «від» і «до».
- Неоплачувані перерви враховуються окремо.
- Фактичні години мають походити з фактичних джерел.
- Похідні/автоматично створені плани можуть перераховуватися за чинним режимом; підтверджений факт — ні.

## 11. Перед кожною зміною

Обов’язковий pre-flight:
1. прочитати `PROJECT_RULES.md`;
2. прочитати `PROJECT_STATE.md`;
3. визначити поточну і наступну ревізію;

5. перевірити, які дані є планом, а які фактом;

## 14. Startup / recovery protocol

- Кожна нова сесія або новий чат Taxo починається з `START_HERE.md`.
- Після нього обов'язково читаються `PROJECT_RULES.md`, `PROJECT_STATE.md`, `WORKLOG.md` і live ledger Issue #61.
- GitHub є фактичним арбітром для branch/PR/SHA/CI/release; текстові файли мають бути синхронізовані з ним.
- `PROJECT_STATE.md` містить підтверджений інтегрований стан, а не незлиті експерименти.
- `WORKLOG.md` містить оперативний active slice і точну наступну дію.
- Кожен завершений slice записується в Issue #61.
- Після обриву не відтворювати стан з пам'яті чату, якщо його можна відновити з GitHub.

## 15. Команда власника «злити у main»

- Фраза власника **«злити у `main` / зливай у `main`»** означає повний релізний checkpoint, а не лише merge PR.
- Для Taxo це включає: завершити поточну ревізію, пройти regression/CI, інтегрувати PR у `main`, синхронізувати документацію, створити immutable tag/release, опублікувати START/source, checksums/legal notices та актуальні Windows/macOS пакети для підтримуваних архітектур, якщо власник не вказав інше.
- Якщо потрібен лише merge без повного релізу, використовувати формулювання **«інтегрувати PR у main»**.
- Після повного checkpoint `PROJECT_STATE.md`, `WORKLOG.md` і Issue #61 мають показувати один і той самий завершений стан та наступну дозволену ревізію.

## 16. UI regression gate

Перед кожним релізним checkpoint і після суттєвої зміни інтерфейсу:

- перевірити головне вікно та змінені `Toplevel` на малому робочому просторі не менше ніж 900×600, 1024×700 і типовому 1366×768;
- окремо врахувати Windows display scaling / збільшені системні шрифти; нижні кнопки дії не можуть залежати від того, чи помістився основний контент;
- нові великі secondary windows мають використовувати `fit_window_to_screen()` або еквівалентний screen-fit механізм;
- якщо форма може бути вищою/ширшою за viewport, кореневий content повинен мати прокрутку або адаптивне компонування;
- широкі `Treeview` повинні мати horizontal scrollbar, якщо сумарна мінімальна ширина колонок може перевищити мінімальну ширину вікна;
- довгі toolbar/action rows не можна будувати з розрахунком лише на широкий desktop: групувати у 2 ряди, adaptive blocks або overflow menu;
- критичні кнопки/навігація не повинні покладатися лише на Unicode/emoji glyph, якого може не бути у Windows 7 font stack;
- перевіряти normal / selected / disabled / hover / keyboard focus contrast;
- platform-specific UI path для Windows, Windows 7 і macOS має мати окремий regression guard, якщо платформа рендерить контрол інакше;
- знайдені UI-дефекти та їхній пріоритет фіксувати у `docs/maintenance/AUDIT_UI_*.md` і `WORKLOG.md`.

UI-gate не замінює функціональні regression tests: обидва набори перевірок обов'язкові.


## Державні реєстри та локальний контроль документів — жорстке розділення

- Поточний контроль документів ТЗ у Taxo є **локальним оперативним обліком підприємства** і працює тільки з записами/копіями документів у Taxo.
- Реєстрова звірка **не змінює, не доповнює автоматично і не визначає статуси** локального контролю документів ТЗ.
- Джерело працівників: Дія/державні облікові витяги — персональні та військово-облікові відомості, які держава веде в обов'язковому обліку.
- Джерело ТЗ: реєстр «Шлях» — відомості про ТЗ та ліцензійну справу перевізника, які відомі державі.
- Відсутність поля/документа в державному реєстрі **не означає** відсутність локального документа підприємства; наявність реєстрового запису **не означає** наявність його копії або чинність локального документа.
- Реєстрова звірка має окремий UI/статус/історію рішень і не повинна вбудовуватися в `vehicle_document_summary`, `control_rows`, попередження шляхівки або інший поточний локальний контроль документів.


## Реєстри як джерело автоматичного наповнення Taxo

- Державний реєстр є не лише джерелом звіряння, а й дозволеним джерелом **автоматичного наповнення робочої БД Taxo** після попереднього перегляду користувачем.
- Якщо корисний реквізит є у підтримуваному державному витягу, але відповідного поля ще немає у моделі Taxo, модель/схема та картка сутності мають бути розширені цим полем; повторний ручний ввід офіційних даних не є цільовим сценарієм.
- Якщо поле вже існує, але порожнє, режим «Доповнити» може заповнити його непорожнім значенням реєстру.
- Режим «Оновити з реєстру + доповнити» може замінити локальне значення тільки непорожнім значенням із реєстру; порожнє/відсутнє у витягу поле **ніколи не очищає** локальне значення.
- Сутність, яка є у реєстрі, але ще відсутня у Taxo (працівник або ТЗ), може бути створена з даних реєстру тільки після preview та явного підтвердження користувача. Неоднозначні/конфліктні збіги автоматично не об'єднувати.
- При створенні працівника з витягу реєстр не призначає йому автоматично роль водія або іншу внутрішню роль підприємства.
- При створенні/оновленні ТЗ статус «Шлях» зберігається як реєстровий статус і не визначає автоматично локальний `active`/виведення з експлуатації.
- Для реєстрових полів зберігати джерело, дату останнього підтвердження та історію імпортів/знімків.
- Базова періодичність звірки підтримуваних державних реєстрів — **один раз на календарний квартал**; повторний імпорт дозволений у будь-який момент.
- Ці правила не змінюють жорстке розділення між реєстровою звіркою та локальним контролем документів ТЗ.

## Режим тестових пакетів під час розробки

- При інтенсивній розробці, коли протягом години може бути кілька кодових ревізій/перевірок, стандартним тестовим пакетом є **START**. Portable/Setup для кожного такого кроку не будувати без окремої потреби, щоб не витрачати CI/ресурси.
- Для завершеного денного або іншого рідшого контрольного checkpoint стандартним пакетом є **Portable**; Setup додається за потреби.
- Команда «злити у main» як повний релізний checkpoint і надалі передбачає актуальні пакети для підтримуваних платформ згідно з релізною політикою.
- Якщо власник окремо вказує тип пакета для конкретної ревізії, пріоритет має ця явна вказівка.

- Executable-пакети містять повні тексти ліцензій сторонніх компонентів, а не лише їхні назви.
