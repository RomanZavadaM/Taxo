# Taxo 10.14-r8 — закріплення водіїв/ТЗ не зникають із наказу та друку

**Дата:** 09.11.2026  
**Тип:** candidate / owner-found data-flow + Feature Loss regression fix.  
**Stable:** без змін, `v10.14-r4`.

## Що показав реальний тест

Власник перевірив наказ №27. Після використання механізму додавання водіїв/ТЗ — як по одній парі, так і масово — у перегляді наказу та створеному DOCX таблиця залишалась порожньою.

Також у вже створеному наказі через «Редагувати наказ» не було прямого доступу до поточного списку закріплень.

## Підтверджена причина порожнього документа

Вікно «Перегляд наказу» читало список закріплень лише один раз — у момент відкриття.

Якщо наказ був створений без пар, Taxo автоматично відкривав порожній перегляд. Після подальшого додавання водіїв/ТЗ відкрите вікно не перечитувало БД. Натискання «Створити DOCX/PDF/JPG» використовувало старий порожній список, тому документ виглядав так, ніби створені пари зникли.

## Виправлено

- перед **кожним** створенням DOCX/PDF/JPG Taxo заново читає актуальний наказ і його закріплення з БД;
- у перегляді наказу додана дія «Оновити зміст»;
- якщо наказ про закріплення створено без пар, після збереження Taxo переводить користувача у вкладку «Закріплення водіїв», а не одразу відкриває порожній друк;
- після одиночного додавання Taxo перевіряє, що вибрана пара реально записана;
- після масового додавання Taxo перевіряє **всі** вибрані пари перед commit;
- така перевірка читає тільки сирі записи й не запускає міграцій усередині транзакції;
- вкладка «Закріплення водіїв» показує фактичну кількість записів вибраного наказу;
- читання закріплень для наказу використовує LEFT JOIN, тому навіть історично пошкоджений зв'язок не може мовчки зникнути лише через відсутність пов'язаної картки працівника або ТЗ;
- у «Редагувати наказ» видно поточний список ТЗ / держномер / водій;
- «Додати багато…» і «Керувати закріпленнями» доступні прямо з існуючого наказу;
- статус наказу та паперовий підпис не блокують ці робочі зміни.

## Контроль від повторної втрати

Сценарій редагування існуючого наказу став окремим 26-м critical route:

`operations.assignment_existing`

Він підключений до строгого gate 10.14-r7: `mapped + onscreen + usable + activation`.

Окремі поведінкові regressions перевіряють:

1. одну пару + масові пари;
2. commit;
3. **закриття БД**;
4. повторне відкриття БД;
5. наявність усіх пар після reopen;
6. передачу всіх пар у спільний `order_layout`, з якого формуються Word/PDF/JPG;
7. сценарій «перегляд уже відкритий порожнім → у БД з'явились пари → Створити DOCX» — генератор мусить отримати вже **свіжі** пари, а текст перегляду оновитися.

Stable / Latest не пересувається без окремого рішення власника.
