# Taxo 10.8-r9 — fast-test

**Статус:** кандидат для тестування / prerelease.  
**База:** immutable `v10.8-r8`.  
**Stable:** `v10.3` не змінюється.

## Мета ревізії

Підготувати Taxo до подальшого масштабного розширення без нарощування нового інфраструктурного коду всередині великого `main.py`.

`10.8-r9` виносить низькорівневі механізми резервної копії, відновлення та одноразової legacy-міграції БД у окремий infrastructure-модуль, зберігаючи чинні public wrappers і поведінку користувача.

## Що змінено

- додано `backup_migration.py`;
- винесено пошук legacy-БД першого запуску;
- винесено одноразове копіювання legacy-БД у поточний workspace;
- винесено узгоджений SQLite backup через `sqlite3.backup()`;
- збережено чинне правило retention останніх 30 SQLite backup-файлів цього механізму;
- винесено добовий auto-backup guard;
- винесено перевірку сумісності/цілісності резервної БД;
- винесено atomic restore через тимчасову БД;
- перед restore як і раніше створюється safety backup поточної БД;
- при помилці restore виконується best-effort rollback із safety backup;
- у `main.py` залишені compatibility wrappers, тому старі call sites не потребують переписування;
- `START.bat` вимагає `backup_migration.py` як обов'язкову частину повного START-пакета;
- додано `tests/test_v10_8_r9.py`;
- додано аудит `docs/maintenance/AUDIT_BACKUP_MIGRATION_INFRASTRUCTURE_v10.8-r9.md`.

## Архітектурна межа

`backup_migration.py` містить тільки SQLite/filesystem mechanics. Він не приймає UI-рішень, не містить Tkinter, не визначає бізнес-правила Taxo і не стає загальним service locator.

Політика робочих даних, 48-місячне зберігання предметних даних, UX резервного копіювання та інші доменні правила лишаються поза цим infrastructure-модулем.

## Що НЕ змінювалося

- формат поточної робочої SQLite-БД;
- структура workspace;
- plan/fact;
- Бланки підтвердження діяльності;
- роль водія;
- табель;
- СТОІР business rules;
- документи ТЗ;
- військовий облік;
- чинна stable `v10.3`.

## Що перевірити вручну

1. Запуск із наявним workspace без міграції старої БД.
2. Ручне створення резервної копії.
3. Відновлення зі справної резервної SQLite-БД.
4. Відмова від відновлення з некоректного/чужого файла.
5. Після restore — наявність даних і нормальний запуск основних розділів.
6. Переключення workspace — backup/restore мають працювати з поточною БД, а не зі старим шляхом.

## Далі

Після r9 наступна кодова зміна — `10.8-r10`. Подальшу декомпозицію робити малими сумісними slices: infrastructure окремо, domain/service/repository/UI окремо, без великого переписування ядра за один крок.

## Важливо

- це fast-test checkpoint;
- PR не зливається в `main` без окремої команди власника;
- після видачі `v10.8-r9` ревізія заморожується;
