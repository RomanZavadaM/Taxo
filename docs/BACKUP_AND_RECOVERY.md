# Резервне копіювання і відновлення Taxo 9.0

## 1. Що є критичними даними

Головна цінність системи — не виконуваний файл Taxo, а робоче сховище. Воно містить бази даних, тахографічні скани, архіви документів, резервні копії та журнали.

Для повного захисту недостатньо копіювати лише `driver_worktime.sqlite3`: потрібно резервувати весь робочий корінь.

## 2. Вбудовані резервні копії

Taxo створює узгоджені SQLite-копії штатними засобами. Такі копії безпечніші за ручне копіювання відкритого файла бази.

Вбудований каталог `Backups` треба включати до зовнішнього резервного копіювання.

## 3. Рекомендована схема

Мінімально рекомендовано мати три рівні:

1. робоче сховище;
2. автоматичні локальні резервні копії Taxo;
3. зовнішню копію на іншому фізичному носії, сервері або контрольованому хмарному сховищі.

Бажано мати хоча б одну копію, яка не синхронізується миттєво з робочою папкою, щоб випадкове видалення або пошкодження не повторилось автоматично всюди.

## 4. Коли робити контрольну копію

Обов'язково перед:

- оновленням на нову основну версію;
- перенесенням робочого сховища;
- масовим імпортом або виправленням даних;
- ручними технічними операціями з файлами;
- заміною комп'ютера або диска.

## 5. Як перевіряти резервну копію

Копія вважається надійною лише якщо її можна прочитати. Періодично перевіряйте:

- чи існує файл резервної бази;
- чи його розмір не дорівнює нулю;
- чи дата копії відповідає очікуваній;
- чи присутні архіви документів і скани;
- чи є достатньо вільного місця.

Для критичного оновлення бажано виконати тестове відкриття копії в окремому тестовому сховищі.

## 6. Відновлення

Не відновлюйте базу поверх активного робочого сховища навмання.

Рекомендований порядок:

1. закрити Taxo на всіх комп'ютерах;
2. зробити копію поточного пошкодженого/сумнівного сховища — навіть якщо воно здається непридатним;
3. створити окрему папку для відновлення;
4. розгорнути туди потрібну резервну копію;
5. підключити Taxo до відновленого сховища;
6. перевірити водіїв, останні табелі, шляхівки, автомобілі, маршрути та тахографічні дані;
7. лише після перевірки визнати відновлене сховище робочим.

## 7. Хмарна синхронізація не є резервною копією

OneDrive, Dropbox або Google Drive зручні для перенесення стану між комп'ютерами, але синхронізація може також поширити помилкове видалення чи пошкоджений файл. Тому потрібна окрема історична резервна копія.

## 8. Що не треба резервувати як робочі дані

Інсталяційні EXE/ZIP можна повторно завантажити з GitHub Releases. Вони не замінюють резервну копію бази і не містять ваших робочих даних.

## 9. Перед зверненням по допомогу

Якщо потрібне відновлення після проблеми, не робіть багато повторних запусків і випадкових копіювань. Збережіть:

- поточне робоче сховище;
- останню відому добру резервну копію;
- журнал `Logs`;
- опис, коли саме помилка стала помітною.
