# Taxo — рішення за рекомендаціями незалежного аудиту dev-strategy v2

**Дата:** 03.11.2026  
**База Taxo:** main `7a581e159fbea6d885030e01f9e933d1467148b4`  
**Stable:** `v10.10-r4`

Мета цього документа — зафіксувати, що команда Taxo прийняла, відклала або відхилила після незалежного read-only аналізу `dev-strategy`.

Стабільна версія **не змінюється лише заради методології**.

## 1. Відновлення після обривів — ПРИЙНЯТО, ВИКОНУЄТЬСЯ ЗАРАЗ

Рішення:
- розділити швидке відновлення стану і повний preflight перед записом;
- quick recovery: START → HANDOFF → live GitHub;
- private profile / PROJECT_RULES / PROJECT_STATE читаються перед внесенням змін;
- WORKLOG та Issue #61 — лише коли потрібні деталі.

Причина: це зменшує час після зависання, але не послаблює правила перед зміною продукту.

## 2. Узгодженість документації — ПРИЙНЯТО, ВИКОНУЄТЬСЯ ЗАРАЗ

Рішення:
- виправити застаріле формулювання HANDOFF;
- `dev-strategy` може аналізувати Taxo read-only і рекомендувати зміни;
- жодна рекомендація не застосовується автоматично;
- запис у Taxo — тільки уповноваженими виконавцями за рішенням власника.

Також надалі при кожному критичному checkpoint звіряти HANDOFF / PROJECT_STATE / live GitHub.

## 3. GitHub Actions для documentation-only — ПРИЙНЯТО, ОКРЕМИЙ CI-SLICE

Проблема підтверджена: навіть documentation-only PR запускали важкі Windows / Windows 7 / macOS збірки.

Рішення:
- не послаблювати фінальний release-контроль;
- для звичайних docs-only змін перейти на легкі checks;
- код, dependencies, packaging, workflow, release/security зміни залишити під повними перевірками;
- старий PR #142 використовувати лише як довідковий матеріал; **не зливати автоматично**. Рішення має бути перевірене на актуальному main окремим CI-slice.

## 4. Безпека збірок — ПРИЙНЯТО В ПРИНЦИПІ, ОКРЕМИЙ SECURITY-SLICE

Перевірити й за потреби посилити:
- pin/identity зовнішніх GitHub Actions;
- provenance сторонніх компонентів;
- dependency і installer-tool controls;
- контроль нових executable / DLL;
- мережевий код;
- автозапуск / фонова активність;
- update-механізми;
- аналіз складу готових release-пакетів.

Чинний license gate зберігається.

Не змішувати security-hardening із функціональною розробкою.

## 5. Захист релізів — ПРИЙНЯТО ДЛЯ ОКРЕМОЇ ПЕРЕВІРКИ

Чинне правило Taxo: опубліковані tags/releases immutable.

Потрібно окремо перевірити:
- що забезпечується процедурою;
- що реально блокується GitHub rules/settings;
- чи можна технічно перемістити tag або змінити release asset;
- які додаткові технічні гарантії доцільні.

До завершення цієї перевірки не заявляти, що процедурна незмінність дорівнює технічній неможливості зміни.

## 6. Незалежний continuity-test — ПРИЙНЯТО, НАСТУПНИЙ КОНТРОЛЬНИЙ ТЕСТ

Новий виконавець без попереднього чату має:
1. відкрити START;
2. відновити фактичний стан;
3. знайти наступну безпечну дію;
4. не читати старі чати;
5. зафіксувати час і місця, де виникла неоднозначність.

Критерій успіху: стан і наступна дія визначаються за кілька хвилин без помилкового повторення вже виконаної роботи.

## Відхилені рекомендації

На цьому етапі **немає відхилених по суті рекомендацій**.

Водночас відхиляється підхід:
- змінювати stable тільки заради відповідності методології;
- автоматично застосовувати зовнішні рекомендації;
- змішувати CI/security/release hardening з іншими функціональними змінами.
