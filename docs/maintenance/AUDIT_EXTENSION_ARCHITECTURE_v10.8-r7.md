# Taxo 10.8-r7 — архітектура розширення

## Мета

Taxo не розглядається як завершений невеликий застосунок. Подальша розробка має допускати суттєве нарощування функціоналу без постійного збільшення одного `main.py` і без переписування точки входу для кожної нової ревізії.

Цей крок не є переходом на мікросервіси і не є великим переписуванням. Поточна модель лишається desktop modular monolith із локальним робочим сховищем та SQLite, але в коді вводяться чіткіші точки розширення.

## Проблема, яку вирішує r7

До r7 `taxo_app.py` містив десятки імпортів історичних feature-layer модулів і довгу вкладену композицію `install(...)`. Кожен новий шар вимагав ручного редагування entry point і збільшував ризик помилки в порядку встановлення.

Це погано масштабується, навіть якщо окремі модулі працюють правильно.

## Рішення r7

Створено `feature_layers.py` — єдиний впорядкований registry runtime-шарів.

Кожен шар має:

- стабільний `feature_id`;
- installer callable;
- ознаку bootstrap тільки для першого базового шару;
- доменну metadata-мітку (`worktime`, `personnel`, `maintenance`, `military-accounting` тощо).

`taxo_app.py` тепер не знає про десятки конкретних revision-layer модулів. Він імпортує один installer registry і будує `App` через нього.

Registry перевіряє:

- унікальність `feature_id`;
- рівно один bootstrap на першій позиції;
- callable installer для кожного шару;
- наявність базового `App` перед наступним extension layer.

## Головний принцип на майбутнє

`feature_layers.py` — це **точка композиції та сумісності**, а не місце для бізнес-логіки.

Новий великий функціонал не слід реалізовувати як нескінченний набір файлів `vXXXX_features.py`.

Нові домени мають рухатися до структури:

1. domain/service модуль — правила й операції;
2. repository/data-access layer — робота з даними конкретного домену;
3. UI layer — представлення та дії користувача;
4. невеликий installer/adapter — підключення домену до Taxo;
5. registry — тільки порядок і metadata.

Історичні revision wrappers поки залишаються, щоб не ламати вже перевірені сценарії. Їх можна консолідувати лише окремими безпечними кроками з regression coverage.

## Межі між доменами

Для майбутнього розвитку закладається правило:

- модуль СТОІР не повинен напряму володіти табелем;
- табель не повинен напряму володіти документами ТЗ;
- військовий облік не повинен змінювати operational active ТЗ;
- документальний центр не повинен створювати паралельні джерела істини;
- plan/fact лишаються різними сутностями;
- історичні дані не видаляються через перехід на новий модуль.

Обмін між доменами надалі має йти через вузькі service/repository interfaces або чітко визначені read models, а не через випадкові імпорти великого `main.py`.

## Напрям наступних ревізій

Після r7 доцільно послідовно:

1. ввести невеликий application/service context для спільних залежностей (`DB path/connection factory`, workspace, output services), не переносити туди бізнес-правила;
2. винести backup/migration інфраструктуру з `main.py`;
3. винести query/helper-шар Бланків без зміни їх fact semantics;
4. нові великі функції одразу створювати окремими доменними модулями;
5. поступово зменшувати залежність нових модулів від `main` як глобального namespace.

## Що r7 НЕ змінює

- схему та вміст робочої БД;
- робочі каталоги користувача;
- СТОІР business rules;
- документи ТЗ;
- Бланки;
- plan/fact;
- роль водія;
- розрахунки табеля;
- порядок історичних feature layers.

## Критерій успіху

Новий модуль Taxo після r7 повинен підключатися однією registry-декларацією і власним installer, а не новою вкладеною конструкцією в `taxo_app.py`. Подальша архітектура повинна дозволяти нарощувати продукт доменами, не перетворюючи entry point або `main.py` на нову єдину точку залежностей.
