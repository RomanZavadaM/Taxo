**База:** `main` `8f18a7ccf1588556f6f3d7dca81943f87d817935`  
**Branch:** `work/v10.9-r2-waybill-integrity`  
**PR:** #121

## Підтверджений дефект базової моделі

До r2 таблиця `waybills` посилалась на `worklog` і `drivers` через `ON DELETE CASCADE`, а `waybill_events` — на `waybills` через cascade. Одночасно startup retention фізично видаляв `worklog` старше 48 місяців. Це означало, що звичайне автоматичне очищення могло знищити видану шляхівку та її журнал подій.

Другий дефект: чинний рядок `waybills` був унікальним по `worklog_id`, а повторна видача після анулювання могла переписувати серію/номер цього самого рядка. Перевірка дубля дивилась на поточний `waybills`, тому попередній анульований номер, який лишився тільки у `waybill_events`, міг знову стати доступним.

## Інваріанти r2

1. Виданий номер є незворотним фактом: `(document_series, document_number)` після першої фіксації більше ніколи не використовується іншою видачею.
2. `waybill_events` використовується як джерело backfill для раніше анульованих/перевиданих номерів.
3. Retention табеля не видаляє `worklog`, якщо він є джерелом виданої шляхівки.
4. Водія з історією виданих шляхівок не можна фізично видалити каскадом.
5. Захист діє на рівні SQLite trigger, тому не залежить від конкретного UI-вікна або старого runtime-layer.
6. Новий код не додається в історичний великий `main.py`: safeguard ізольований у `waybill_integrity.py`.

## Міграційна поведінка

`ensure_schema_on_connection()` є additive/idempotent:

- створює `waybill_number_history`, якщо таблиці ще немає;
- спочатку імпортує номерну історію з `waybill_events`, потім поточні номери з `waybills`;
- використовує `INSERT OR IGNORE`, тому повторний startup не дублює історію;
- після backfill встановлює INSERT/UPDATE/DELETE guards.

Жоден існуючий номер не видаляється і не перенумеровується.

## Поведінкові тести

`tests/test_v10_9_r2.py` перевіряє на реальній SQLite-БД:

- старий `worklog` без шляхівки очищається, але старий `worklog` із шляхівкою лишається;
- анульований номер backfill-иться з журналу і не може бути повторно вставлений після перевидачі;
- новий номер перевидачі також стає історично зайнятим;
- DELETE захищеного `worklog` або `driver` завершується `IntegrityError`.

Exact candidate regression на `4708330587024fc94dda58621cd46fee0faf744e`: **734/734 OK**, source archive `Taxo_v10_9_candidate_r2_START.zip` створено й перевірено.

## Залишок r2 перед issuance

- перевірити exact-head Windows та macOS gates після фінальних docs commits;
- окремо оцінити атомарність «БД + створення PDF». SQLite-транзакція не може зробити файлову систему атомарною, тому безпечна модель повинна бути `temporary file → DB transaction → atomic rename/compensating cleanup`, а не утримувати транзакцію під час довгого PDF renderer;
- не видавати immutable `v10.9-r2`, доки цей залишок та platform gates не закриті або явно не винесені окремим наступним revision із документованою межею.

## Не входить у r2

Документи ТЗ, правила відпочинку, тахограф/60 днів, П-5, СТОІР та накази зафіксовано окремим audit backlog і не змішуються з цим PR.
