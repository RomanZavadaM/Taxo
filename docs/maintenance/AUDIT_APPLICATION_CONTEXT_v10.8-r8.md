# Taxo 10.8-r8 — application services / межа інфраструктури

## Мета

Після r7 Taxo має впорядкований registry runtime feature layers. Наступна проблема масштабування — старі feature-модулі отримують увесь модуль `main` і можуть напряму звертатися до будь-яких глобальних змінних, UI helper-ів і функцій. Для історичних шарів це лишається сумісністю, але для нового великого функціоналу така залежність не повинна ставати нормою.

r8 вводить **вузький application-services context** для нових модулів.

## Що є application context

`application_context.py` надає тільки спільну інфраструктуру:

- `WorkspaceServices` — поточне робоче сховище, його шляхи та нове SQLite connection до головної БД;
- `OutputServices` — спільний запис/відкриття вихідних файлів і шрифти звітів;
- `ApplicationServices` — агрегований контракт і поточна версія програми.

Контекст не зберігає snapshot шляхів. Він кожного разу читає актуальний workspace root, тому переключення робочого сховища не залишає нові модулі на старій БД.

## Як підключаються нові feature layers

`FeatureLayer` отримав metadata `uses_services`.

Історичні шари продовжують викликатися без змін:

- bootstrap: `install(core)`;
- extension: `install(core, App)`.

Новий шар може явно вибрати новий контракт:

- bootstrap: `install(core, services)`;
- extension: `install(core, App, services)`.

Після композиції `App.services` містить той самий `ApplicationServices`, тому новий UI може використовувати `self.services` без імпорту глобального `main`.

## Чому це важливо для подальшого росту

Taxo планується значно більшим за поточний стан. Без цієї межі кожен новий модуль міг би накопичувати приховані залежності від `main`, що ускладнює тестування, заміну реалізацій, роботу з кількома доменами та подальшу декомпозицію.

Новий підхід дозволяє поступово перейти від «модуль бачить всю програму» до «модуль отримує тільки потрібну інфраструктуру» без масового переписування вже перевірених історичних шарів.

## Жорстка межа

`ApplicationServices` **не є service locator для бізнес-логіки**. У нього не слід додавати:

- правила plan/fact;
- розрахунки табеля;
- правила Бланків;
- правила СТОІР;
- військовий облік;
- кадрові рішення;
- генерацію конкретного бізнес-документа.

Такі речі повинні жити у власних domain/service модулях. Context дає їм лише інфраструктуру.

## Наступний напрям

Після r8 можна безпечніше виносити з `main.py` окремі інфраструктурні блоки. Перший кандидат — backup/migration orchestration, тому що він використовує workspace/DB/filesystem і добре лягає на новий explicit context.

Паралельно новий функціонал слід одразу будувати окремими доменними пакетами/модулями з repository/service/UI межами, а не додавати великі блоки у `main.py`.

## Що r8 НЕ змінює

- схему робочої БД;
- існуючі таблиці та дані;
- формат workspace;
- порядок історичних feature layers;
- plan/fact;
- Бланки;
- роль водія;
- табель;
- СТОІР business rules;
- документи ТЗ;
- військовий облік;
- backup semantics.

## Контроль регресій

`tests/test_v10_8_r8.py` перевіряє:

- workspace services бачать зміну root без кешування старого шляху;
- DB connection відкривається до актуальної workspace DB;
- context не містить business-domain APIs;
- context-aware layer отримує services;
- legacy installer signature залишається робочим;
- context-aware layer без context завершується явною помилкою;
- runtime entry point реально створює та передає application services.
