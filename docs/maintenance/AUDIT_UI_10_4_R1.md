# AUDIT_UI_10_4_R1 — аудит інтерфейсу Taxo

**Дата:** 25.09.2026  
**База аудиту:** `main` після full checkpoint `v10.4-r1`  
**Мета:** знайти не бізнес-логічні, а саме UI/UX дефекти: обрізання, переповнення, слабку читабельність, неадаптивні вікна, дублювання навігації та platform-specific ризики.

## Резюме

Інтерфейс уже має сильні базові механізми — `fit_window_to_screen()`, scrollable body для «Налаштування» та «Підтвердження діяльності», горизонтальні скролбари у великих таблицях, окремий macOS sidebar fix. Але ці механізми застосовані **непослідовно**.

Виявлено:
- **1 підтверджений layout bug з перекриттям контролів**;
- **5 високопріоритетних зон переповнення/обрізання**;
- **кілька системних проблем адаптивності** на 900–1024 px, Windows scaling та старих Windows;
- **інформаційну неузгодженість навігації «Працівники / Персонал / Водії»**;
- **контрастні та platform-font ризики**.

## P0 — підтверджений дефект

### UI-01. «Точка маршруту»: кнопка «Зберегти» накладається на поле форми

У `main.py -> route_catalog_form() -> stop_form()` поля створюються в рядках `0..6`, але кнопка «Зберегти» поставлена в `row=4`.

Наслідок:
- кнопка потрапляє в той самий grid-row, де вже є поле «Відправлення, день D+»;
- залежно від Tk/OS/DPI елементи можуть перекриватися або один з них стає погано доступним.

Правильний напрямок: footer/button row після всіх полів (row 7 або окремий footer).

## P1 — високий пріоритет

### UI-02. Document Viewer не використовує screen-fit

`document_viewer.py`:
- Raster viewer: `1050x780`, min `720x520`;
- DOCX viewer: `980x720`, min `700x500`.

На екрані 1366×768 перше вікно вже вище типової доступної робочої області після taskbar/menu. На менших/масштабованих екранах нижня частина може виходити за межі.

Додатково toolbar Raster viewer має 8 дій/індикаторів у **одному рядку**, без wrap/overflow menu.

### UI-03. Контроль документів ТЗ: ширина колонок > мінімальної ширини вікна, але немає horizontal scrollbar

`vehicle_documents.py -> open_vehicle_document_control()`:
- geometry `1100x680`, min `850x500`;
- сумарна базова ширина колонок ≈ **970 px**;
- є тільки vertical scrollbar.

При зменшенні до 850 px частина колонок фізично недоступна.

### UI-04. «Працівники»: toolbar гарантовано переповнюється на вузькому main-window

На сторінці реєстру в одному горизонтальному рядку:
- «Звільнити / поновити»;
- «Режим робочого часу…»;
- «Планування…»;
- «Відсутності…»;
- «Тижневий баланс…»;
- «Оновити»;
- окремо справа — «Пошук» + Entry width 28.

Main window допускає ширину близько 900 px, але sidebar займає 176 px плюс padding workspace. Реальна ширина контенту може бути близько 700 px — цей toolbar у неї не вміщується.

### UI-05. «Звіти» у персоналі не має вертикального scroll-body

Reports page містить:
- параметри періоду;
- дату;
- active filter;
- реквізити П-5;
- довге пояснення;
- 5 кнопок в одному рядку;
- блок звітів ТЗ.

Сторінка пакується напряму в hidden notebook без canvas/vertical scroll. На невисокому екрані нижні блоки можуть стати недоступними.

Додатково `wraplength=980/900` може примусово розширювати content ширше за доступну область.

### UI-06. «Табель персоналу»: декілька toolbars без адаптивного перенесення

`show_employee_timesheet()` має:
- верхній row фільтрів;
- `toolbar_actions`;
- `toolbar_reports`;
- `edit_bar`;
- `report_bar`.

У `report_bar` ще є довгий пояснювальний текст справа. Навіть при screen-fit до ~944 px (1024 px screen) кнопки та пояснення можуть обрізатися.

## P2 — середній пріоритет

### UI-07. Main header занадто щільний для 900–1024 px

Header має fixed height 116 px і в одному горизонтальному pack:
- logo;
- назву підприємства;
- slogan;
- дату/час;
- користувача;
- кнопку «Налаштування»;
- hamburger menu.

На широкому екрані виглядає добре, але при 900–1024 px slogan фактично є єдиним блоком, який може стискатися. Правий блок і назва підприємства можуть обрізатися, особливо при довгій назві або DPI scaling.

### UI-08. Sidebar не має vertical scrolling / compact mode

Sidebar fixed width 176 px і містить 9 навігаційних пунктів + декоративний road block.

При невисокому екрані / 125–150% scaling немає механізму:
- прокрутити navigation;
- зменшити spacing;
- сховати decoration;
- перейти в compact/icon-only mode.

### UI-09. Планувальники персоналу: великі Treeview без horizontal scrollbar

Зокрема:
- «Норма за режимом → план місяця»: колонки ≈ 780 px, min window 720 px;
- «Масове планування змін»: колонки ≈ 835 px, min window 780 px;
- «Відсутності»: колонки ≈ 870 px, min window 760 px.

У цих таблицях є vertical scrollbar, але немає horizontal scrollbar.

### UI-10. Vehicle Documents і edit form не використовують загальний screen-fit helper

`VehicleDocumentsWindow` — fixed `1050x650`; form — fixed `660x520`.

Це не так критично як document viewer, але суперечить уже введеному правилу screen-fit. На старих ноутбуках / scaling нижні дії можуть опинятися близько до краю.

### UI-11. Поле «Примітка» часто зроблене однорядковим Entry

У документах ТЗ та частині інших форм примітка — `Entry`, хоча за змістом це багаторядковий текст. Довгі примітки важко читати й редагувати.

### UI-12. Navigation model «Працівники / Персонал / Водії» не до кінця уніфікований

Після встановлення personnel module:
- sidebar «Працівники» відкриває новий реєстр персоналу;
- main notebook все ще містить legacy tab «Водії»;
- menu «Розділи» містить і «Персонал», і «Водії».

Це функціонально допустимо, але інформаційно виглядає як два реєстри людей. Потрібно або чітко назвати «Водійські картки», або зробити один entry point з підрозділом водійських даних.

## P3 — polish / accessibility

### UI-13. Низький/граничний contrast частини кольорів

За palette:
- `warning #E49B00` на `warning_soft #FFF4D2` ≈ **2.13:1**;
- `muted #667A8D` на `paper #F4FAFD` ≈ **4.21:1**;
- білий на accent `#087FC3` ≈ **4.34:1**.

Помаранчеві показники особливо слабкі. Крім того, у коді багато `foreground="gray"`, що на слабких/старих дисплеях читається гірше.

### UI-14. Unicode glyph icons ризиковані для Windows 7

У функціональних елементах лишаються символи:
`⚙`, `☰`, `ⓘ`, `▣`, `＋`, `●`, `◀/▶`.

У коді вже є правильний прецедент: calendar button відмовився від emoji через проблеми font rendering. Після офіційної підтримки Windows 7 цей принцип варто застосувати до всіх критичних navigation/action glyphs.

### UI-15. Fixed Treeview rowheight = 26 та fixed header/status heights

Theme задає `Treeview rowheight=26`; main header = 116 px, status bar = 34 px.

При системному збільшенні шрифту ці fixed heights можуть стати меншими за фактичний текст/контрол.

### UI-16. Linux mouse-wheel support у scrollable tab helper неповний

`_make_scrollable_tab_body()` слухає `<MouseWheel>` / Shift-MouseWheel, але не X11 `<Button-4>/<Button-5>`. Scrollbars є, тому блокування роботи немає, але колесо миші на частині Linux/Tk може не працювати.

## Системна причина

Головна причина більшості UI-дефектів — **непослідовність layout policy**:
- частина вікон використовує `fit_window_to_screen()`;
- частина має hard-coded geometry;
- лише деякі складні сторінки мають scrollable root;
- horizontal toolbars не мають adaptive overflow;
- таблиці не всюди отримують обидва scrollbar-и.
