# Аудит суміжників — прийняті в роботу знахідки

**Дата:** 01.10.2026  
**База:** інтегрований Taxo 10.9-r1 / `main`  
**Статус:** прийнято в роботу; перевіряти кожен пункт на актуальному runtime перед зміною.

Цей документ фіксує не «сліпе прийняття» стороннього аудиту, а перевірені або достатньо обґрунтовані ризики, які беремо у план Taxo. Для критичних правил обов'язкові поведінкові тести на реальній тимчасовій SQLite-БД. Source-string guards не вважаються достатнім доказом правильної бізнес-поведінки.

## P0 — цілісність юридично/операційно значущої історії

### 10.9-r2 — шляхові листи

Беремо в роботу:

- 48-місячний retention `worklog` не повинен каскадно знищувати `waybills` та `waybill_events`;
- серія+номер після першої видачі ніколи не повертаються в доступний пул, навіть після анулювання;
- повторна видача після анулювання не повинна стирати ідентичність попередньої видачі;
- водія або `worklog`, на які вже спирається видана шляхівка, не можна фізично видалити каскадом;
- видача має рухатися до атомарної схеми БД+файл, щоб збій не лишав PDF без запису або запис без коректного файла.

Перший r2 крок: DB-level незворотний реєстр використаних номерів + retention guards + поведінкові тести.

### 10.9-r3 — документи ТЗ

- оперативна перевірка враховує `valid_from`, а не лише дату завершення;
- майбутній поліс не може перекривати розрив до початку своєї дії;
- для багатоденного рейсу контроль покриває весь інтервал рейсу.

### 10.9-r4 — робочий час та відпочинок

- контроль від межі вікна аналізу до першого кваліфікованого відпочинку та від останнього до кінця;
- не допускати ситуації «кваліфікованих відпочинків немає → попереджень немає»;
- окремо контролювати короткий міжзмінний відпочинок із урахуванням законних розділених схем;
- перекриття змін трактувати як помилку даних, а не тихо зливати;
- додати двотижневі правила;
- чітко розділити PLAN і FACT контроль.

## P1 — достовірність модулів

### 10.9-r5 — тахограф / 60-денний реєстр

- непідтверджений авто-кандидат нижче за будь-який людський/фактичний запис;
- 24-годинний інтервал не перетворюється на нуль;
- перевіряти перекриття інтервалів;
- окремо змоделювати час вставки аналогової шайби, а не лише дату;
- прибрати витоки з'єднань у статистиці;
- не відкидати довгі сліди мовчки — показувати як невизначені/підозрілі дані.

### 10.9-r6 — персонал, баланс, П-5

- плановий «Вихідний/Відпочинок» не повинен автоматично зменшувати норму так само, як відпустка/лікарняний;
- при повторному прийнятті працівника не губити неявки через однозначний `{driver_id: employee_id}` mapping;
- перевірити 2/2, 3/3 та інші індивідуальні режими поведінковими тестами.

### 10.9-r7 — СТОІР

- `work_date` є fallback-датою для показника одометра, якщо `reading_at` порожній;
- `latest_odometer` не ігнорує новіший фактичний показник зі шляхівки;
- `average_daily_mileage` використовує валідні точки з fallback-датою;
- прогноз іде від дати останньої надійної точки, а не сліпо від `date.today()`;
- захистити середній пробіг від одиничних очевидних викидів;
- окремо затвердити бізнес-правило: чи ТО-2 закриває/скидає цикл ТО-1.

### 10.9-r8 — накази

Стара свідома політика дозволяла редагувати затверджений наказ із журналом змін. Для майбутньої моделі беремо жорсткіший інваріант:

- затверджений або підписаний наказ незмінний;
- виправлення оформлюється новим наказом/наказом про зміну;
- скасований наказ не можна повторно затвердити;
- нове закріплення повинно коректно завершувати попереднє, якщо воно взаємовиключне;
- виявляти одночасні конфліктні закріплення водія за ТЗ;
- `update_order()` не повинен очищати `control_employee_id`, коли параметр не передано.

## P2 — надійність та архітектура

Беремо у послідовний технічний борг:

- `PRAGMA user_version` і централізований schema migration path;
- заборона старішій збірці відкривати новішу несумісну схему;
- connection lifetime через `try/finally`, context/transaction boundaries і `data_access.py`;
- поступове усунення широких `except Exception: pass` у критичних шляхах;
- прибрати обов'язковий PyMuPDF із запуску програми;
- повна disaster-recovery копія має включати workspace-документи/скани або явно попереджати, що це лише DB-backup;
- поступово згортати runtime version layers у доменні модулі `domain → service → repository/data access → UI adapter`;
- першочерговий кандидат на доменне згортання після критичних виправлень — аналіз робочого часу.

## Що не прийнято як підтверджений баг

- назва `Бланк підтвердження.docx` в актуальному GitHub коректна; `#U0411…` вигляд був артефактом способу розпакування/представлення у сторонньому середовищі. ASCII alias може бути доданий пізніше як кросплатформний hardening, але це не підтверджена поточна поломка.

## Тестова політика після аудиту

Для кожного критичного правила потрібен поведінковий сценарій, наприклад:

- старий `worklog` виходить за retention, але видана шляхівка і її події лишаються;
- анульований номер неможливо видати повторно;
- майбутній страховий поліс не покриває дату до `valid_from`;
- 40 днів без щотижневого відпочинку дають порушення;
- авто-кандидат тахографа не перекриває підтверджений факт;
- плановий вихідний не створює фіктивне зменшення норми;
- новіший одометр зі шляхівки впливає на прогноз ТО.

Історичні source-string тести залишаються лише там, де вони захищають упаковку, entrypoint або immutable compatibility contract; нову бізнес-логіку ними не доводимо.
