# Правила розробки Taxo

Цей документ є обов’язковим правилом для всіх наступних робочих кроків Taxo.

## 1. Один завершений крок = одна нова ревізія

- Кожен окремий завершений крок розробки, переробка або виправлення отримує нову ревізію.
- Послідовність у межах однієї версії: `r1`, `r2`, …, `r10`.
- Одну й ту саму ревізію не можна повторно використовувати для іншого тестового стану.
- Після того як користувачу видано тестовий архів певної ревізії, наступна зміна починається вже з наступної ревізії.

Приклад:
`10.2-r4 -> 10.2-r5 -> ... -> 10.2-r10 -> 10.3-r1`.

## 2. Після r10 автоматично піднімається друга цифра версії

- `10.2-r10 -> 10.3-r1`.
- `10.3-r10 -> 10.4-r1`.
- Перший розряд (`10 -> 11`) автоматично не змінюється; це робиться лише за прямим рішенням власника проєкту.

Функція `release_naming.next_candidate_version()` і regression-тести закріплюють це правило в коді.

## 3. Ревізія синхронізується всюди

Перед тестовим пакетом однакову ревізію повинні мати:
- `main.APP_VERSION`;
- `VERSION.txt`;
- назва робочої гілки/PR;
- release notes поточного candidate;
- назва START-архіву;
- назва кореневої папки всередині архіву;
- regression-тести поточної ревізії;
- `PROJECT_STATE.md`.

## 4. Кожен завершений крок закінчується тестовим архівом

Робота не вважається завершеною після commit/push або навіть після зеленого CI.

Обов’язково:
1. пройти source regression suite;
2. зібрати START-пакет;
3. перевірити відсутність БД, кешів і персональних даних;
4. дати користувачу пряме посилання на готовий архів для ручного тестування.

Наступний крок починається тільки з нової ревізії.

## 5. Формат тестового START-пакета

Для candidate `10.2-r4`:
- файл: `Taxo_v10_2_candidate_r4_START.zip`;
- всередині рівно одна коренева папка: `Taxo_v10_2_candidate_r4_START/`;
- вкладеного другого ZIP бути не повинно;
- commit-хешів, `(1)`, `(2)` тощо в канонічній назві бути не повинно.

GitHub Actions artifact має бути вже кінцевим ZIP для ручного тестування, а не ZIP-обгорткою з іншим ZIP усередині.

## 6. Stable не переписується

- `main` + останній stable tag лишаються незмінною експлуатаційною базою до ручного прийняття candidate.
- Старі candidate tags/releases не пересуваються.
- Наступний робочий крок створюється від актуальної робочої лінії з новою ревізією.
