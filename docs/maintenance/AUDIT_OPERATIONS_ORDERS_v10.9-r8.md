# Аудит наказів і закріплень — Taxo 10.9-r8

**Дата:** 01.10.2026  
**База:** immutable `v10.9-r7` → `88fcfb20e8632178b095a99ef9b09c86701a072e`  
**Branch:** `work/v10.9-r8-orders-immutability`

## Підтверджені ризики

Перевірка актуального `operations_orders.py` підтвердила всі ключові пункти зовнішнього аудиту:

1. `update_order()` дозволяв змінювати наказ після `approved` і після позначки підписаного паперового оригіналу.
2. `approve_order()` не блокував повторне затвердження скасованого наказу.
3. `update_order()` перетворював непереданий `control_employee_id` на `NULL` через старий default `None`.
4. Закріплення ТЗ/водія, що належали вже затвердженому наказу, можна було додавати, редагувати й видаляти.
5. Не було системного контролю взаємовиключних одночасних закріплень одного водія за різними ТЗ.
6. Новий наказ про закріплення не мав механізму завершення попереднього закріплення без переписування старого наказу.

## Рішення r8

### Незмінність наказу

Затверджений (`approved`) або позначений як підписаний паперовий наказ стає незмінним за змістом. Виправлення має оформлятися новим наказом/наказом про зміну. Скасований наказ також не редагується і не може бути повторно затверджений.

Позначку про підписаний паперовий оригінал після встановлення не можна зняти як звичайне редагування.

### `control_employee_id`

Новий wrapper розрізняє:

- параметр **не передано** → зберегти поточного відповідального;
- `control_employee_id=None` передано явно → очистити поле в чернетці.

### Закріплення водія за ТЗ

Закріплення, що входять до затвердженого/підписаного наказу, незмінні.

Щоб новий наказ міг завершити попереднє закріплення без переписування старого юридичного документа, r8 додає таблицю `vehicle_driver_assignment_endings`. Вона зберігає окремий факт: яке попереднє закріплення, яким новим наказом і якою датою припинене.

При затвердженні нового наказу:

- конфліктні перекривні закріплення одного водія за різними ТЗ у межах самого нового наказу блокують затвердження;
- якщо знайдене одне однозначне попереднє чинне закріплення цього водія, воно операційно завершується днем перед початком нового;
- рядок старого закріплення і старий затверджений наказ **не переписуються**;
- якщо історичні дані вже містять кілька одночасних чинних закріплень одного водія, r8 не вгадує, яке з них правильне: затвердження блокується до усунення конфлікту.

`active_driver_assignments()` враховує окремий факт припинення.

## Реалізація

Додано additive runtime layer `v1098_orders_immutability.py`.

- старий `operations_orders.py` не переписується;
- UI використовує спільний модуль `operations_orders`, тому runtime-layer підміняє доменні операції централізовано;
- schema change additive: одна таблиця фактів припинення, без міграції/переписування існуючих наказів;
- зміни журналюються через чинний `operations_change_log`.

## Поведінкові тести

`tests/test_v10_9_r8.py` перевіряє на тимчасовій SQLite-БД:

- непереданий `control_employee_id` не очищається;
- явний `None` може очистити поле лише в чернетці;
- approved/signed наказ не редагується;
- signed mark не знімається;
- cancelled наказ не затверджується повторно;
- assignment під approved наказом не редагується/не видаляється/не доповнюється;
- новий наказ завершує одне попереднє закріплення без зміни його рядка;
- одночасне конфліктне закріплення одного водія за різними ТЗ у новому наказі блокує approval.
