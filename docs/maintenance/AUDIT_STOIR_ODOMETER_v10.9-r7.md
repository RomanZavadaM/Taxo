# Аудит СТОІР — одометр і прогноз ТО — Taxo 10.9-r7

**Дата:** 01.10.2026  
**База:** immutable `v10.9-r6` → `531723c1b7e9cb9c3d0258d085819381981de14c`  
**Slice:** `10.9-r7`  
**Branch:** `work/v10.9-r7-stoir-odometer-safety`

## Перевірені знахідки

Пункти зовнішнього аудиту перевірено на актуальному runtime перед зміною коду.

### 1. `work_date` як fallback — підтверджено

Старий `latest_odometer()` сортував записи без `reading_at` після датованих записів, навіть коли для такого запису є `work_date`. Тому фактичний показник зі шляхівки міг бути новішим за ручний запис, але не ставати поточним.

**r7:** `reading_at` лишається пріоритетною датою; якщо вона порожня/непридатна, використовується `work_date`. Повністю недатовані записи не використовуються для прогнозної хронології.

### 2. Новіший фактичний одометр зі шляхівки — підтверджено

Через попередню логіку сортування новіший `waybill`-показник без `reading_at` міг програти старішому датованому ручному запису.

**r7:** поточний одометр вибирається за ефективною датою `reading_at -> work_date`, а при однаковій даті — за новішим `id`.

### 3. `average_daily_mileage()` і fallback-дата — підтверджено

Старий розрахунок відкидав усі записи з порожнім `reading_at`, навіть якщо відома `work_date`.

**r7:** середній пробіг використовує ті самі валідні ефективні дати, що й `latest_odometer()`.

### 4. Прогноз від `date.today()` — підтверджено

Старий `vehicle_plan()` викликав `forecast_due_date()` без `from_date`, тому дата прогнозу автоматично відраховувалась від сьогодні, а не від дати останнього фактичного одометра.

**r7:** прогноз відраховується від `effective_date` останньої надійної точки. Якщо надійної дати немає, r7 не вигадує прогнозну дату.

### 5. Одиничний очевидний викид — підтверджено

Старий середній пробіг використовував тільки крайні точки; одинична помилкова різка зміна могла суттєво спотворити прогноз.

**r7:** розрахунок переходить на позитивні хронологічні сегменти. За наявності достатньої історії застосовується робастний статистичний фільтр (median/MAD); для однакової нормальної швидкості з нульовим MAD відсікається лише ізольований >4x стрибок. На малій вибірці дані не відкидаються навмання.

### 6. Чи ТО-2 скидає цикл ТО-1 — не змінюємо без рішення власника

Поточна модель веде останні події ТО-1 і ТО-2 окремо. Зовнішній аудит правильно позначив це як **бізнес-рішення**, а не доведений програмний дефект.

**r7 навмисно зберігає чинну поведінку:** ТО-2 не переписує і не скидає останню подію ТО-1. Це окреме правило для майбутнього явного рішення, якщо буде потрібно.

## Реалізація

Додано `v1097_stoir_odometer.py` як additive runtime layer без зміни схеми БД. Layer:

- читає існуючу `vehicle_odometer_readings` через runtime schema introspection;
- не змінює історичні записи;
- підміняє тільки обчислювальні функції СТОІР: `latest_odometer`, `average_daily_mileage`, `forecast_due_date`, `vehicle_plan`;
- синхронізує історичні aliases у `main.py`, щоб старі entry points використовували ту саму логіку;
- не змінює CRUD одометра, шляхівок, подій ТО або заявок на ремонт.

## Поведінкові тести

`tests/test_v10_9_r7.py` перевіряє на тимчасовій SQLite-БД:

- fallback `work_date`;
- пріоритет новішого waybill-факту;
- historical lookback без прив'язки до системного «сьогодні»;
- захист від одиничного очевидного викиду;
- прогноз від дати останнього фактичного показника;
- незмінність окремих циклів ТО-1 / ТО-2;
- обов'язкову присутність r7 runtime у START package guards.

## Межі зміни

- схема БД не змінюється;
- жоден факт одометра не переписується;
- `v10.9-r6` не змінюється;
- `main` не змінюється до окремої прямої команди власника;
- r7 має пройти exact-head regression, START, Windows і macOS gates перед immutable issuance.
