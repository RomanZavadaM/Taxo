# Taxo — аудит узгодженості навігації та вікон (12.11.2026)

**Статус:** первинний аудит за кодом і скриншотом власника; не є підтвердженням ручного проходження всіх екранів. База — тестова 10.17-r1; робота — 10.17-r2. Документи, бібліотека шаблонів та сховище документів **поза межами змін**.

## Правила для всього інтерфейсу

1. **Головна сторінка / підсторінка у workspace:** коли внутрішні вкладки приховані, на сторінці потрібна видима команда «← До ...» із визначеним призначенням. «Закрити» — лише для окремих вікон, а не для вкладки, щоб не створювати хибне очікування закриття всієї програми.
2. **Діалог або дочірнє Toplevel:** очевидна кнопка «Закрити» або «Скасувати», коректне закриття через стандартний X; збереження — лише окремою явною дією, без неочікуваної зміни даних при виході.
3. **Таблиці:** заголовки сортуються послідовно, коректно для чисел/дат/тексту, фільтри і пошук не зникають, вибір рядка лишається визначеним після refresh. Спільний модуль існує з 10.17-r1, але застосований лише до ТЗ.
4. **Кнопки й команди:** зрозуміла назва дії, стабільне розташування первинної дії та виходу; не дублювати однакові панелі або вкладені головні меню.
5. **Вузькі екрани / DPI:** усі первинні дії досяжні без обрізання; якщо панель переповнюється — перенос або прокрутка, а не приховування.
6. **Безпека:** жодне виправлення навігації не змінює БД, накази, документи, робочий час, резервні копії та історію.

## План наступних проходів

- **A (високий пріоритет):** вручну відкрити кожний основний пункт з лівого меню; дочірню сторінку/вікно; перевірити вихід та повторне відкриття.
- **B:** у кожному діалозі звірити «Зберегти», «Скасувати», X, Escape (якщо заявлено); жодних втрат введених даних без попередження.
- **C:** для кожної таблиці скласти перелік колонок із типами даних, пріоритет сортування та фільтрів.
- **D:** масштабування Windows 100/125/150 %, ноутбучна ширина, macOS Intel/ARM, сумісність Win7; тест CI не є заміною фізичного UI-приймання.

## Межа r2

Внести явну навігацію для трьох прихованих сторінок персоналу, кнопку закриття окремого центру експлуатації та regression; жодних змін даних або інших workflow. Решта — **черга на перевірку, а не вже виправлені дефекти**. Це захищає від широкої одночасної зміни інтерфейсу без приймання.


## Прохід r3 — самостійні робочі центри

- Перевірено структуру `vehicle_maintenance_ui.open_maintenance_center`: якщо центр уже відкритий, повторний виклик піднімає існуюче вікно; якщо його знищено, створюється новий. Видима команда «Закрити» викликає тільки `win.destroy`, не змінює факти ТО/ремонту.
- Перевірено центр `military_transport_ui`: аналогічний Toplevel із повторним відкриттям через перевірку існування; додано «Закрити», без змін військового статусу, прив'язок або інших облікових даних.
- На рівні вихідного коду встановлено, що в СТОІР є окремі діалоги профілю періодичності ТО, запису ТО/ремонту, заявки та її закриття. Не слід масово прив'язувати Escape/X або додавати знищення вікна до їхнього збереження без перевірки проміжного введення.
- У модулі тахографа є допоміжні Toplevel для інтервалів, сканів, статистики та протоколів. У модулі маршрутів і додаткових кадрових форм потрібен окремий огляд; відсутність знайденого буквального `text="Закрити"` ще не доводить несправності: кнопка може бути сформована через helper.
- **Обмеження приймання:** r3 має source regression і платформні CI. Інтерактивні X/«Закрити»/повторний вхід на реальному Windows та масштабування DPI ще не підтверджені.

### Наступна група

1. Перевірити дочірні діалоги СТОІР на «Зберегти»/«Скасувати»/X, відсутність побічного збереження та роботу повторного входу.
2. Аналогічно перевірити тахографічні вікна й маршрути.
3. Окремим кроком застосувати спільне сортування до реєстру працівників і решти таблиць, визначивши типи колонок.


## Прохід r4 — дочірні діалоги СТОІР

**Статичний аудит:** перевірено чотири сценарії: налаштування профілю/періодичності ТО, запис виконаного ТО/ремонту, створення заявки, зміна стану заявки («Взяти в роботу» / «Закрити з результатом»).

| Сценарій | Збереження | Скасування | Статус |
|---|---|---|---|
| Профіль періодичності ТО | Окрема команда «Зберегти профіль» | «Скасувати» уже існувало | Регресійно захищено у r4 |
| Запис ТО / ремонту | Окрема команда «Зберегти» | **Додано «Скасувати» у r4** | Немає запису при скасуванні за контрактом callback |
| Нова заявка | Окрема команда «Створити заявку» | **Додано «Скасувати» у r4** | Немає запису при скасуванні за контрактом callback |
| Зміна стану заявки | «Взяти в роботу» / «Закрити заявку» | **Додано «Скасувати» у r4** | Немає зміни стану при скасуванні за контрактом callback |

Кожна нова дія «Скасувати» викликає лише `dialog.destroy`. Штатна кнопка X також знищує діалог без виклику callback збереження; окремий `WM_DELETE_WINDOW` у цих формах не встановлено. Регресійні перевірки підтверджують структуру callback, але **не заміняють ручного випробування із введеними незбереженими полями**. Попередження про незбережені зміни в r4 не впроваджували: це окрема UX-поведінка, яку потрібно узгодити для всіх форм, а не додавати вибірково.

**Ще не перевірено вручну:** Windows 100/125/150 % DPI; межі доступності нижніх кнопок; Enter/Escape; поведінка при вкладених вікнах; повторне відкриття після X/Скасувати; довгі повідомлення помилок.

### Наступна група після r4
- Тахограф: перегляд сканів, інтервали, статистика, протоколи — інвентаризація виходу та стану незбережених полів.
- Маршрути та решта діалогів Експлуатації: перевірка X/Скасувати/Зберегти, повторний вхід.
- Реєстр працівників й інші таблиці: впровадження спільного сортування з окремим типом для дат (не сортувати дати як звичайний текст).

## Прохід r5 — дочірні вікна тахографа

**Статичний аудит:** перевірено всі чотири Toplevel-сценарії в `TachographModule`, що знайдені у поточному коді.

| Сценарій | Стан до r5 | Рішення r5 |
|---|---|---|
| Підсумкова статистика тахокарти | Окрема кнопка «Закрити» → `win.destroy` | Без змін; вихід уже явний |
| Перегляд скану | Окрема кнопка «Закрити» → `win.destroy` | Без змін; прокрутка та режими перегляду не зачіпалися |
| Протоколи контролю | Окрема кнопка «Закрити» → `win.destroy`, але горизонтальний scrollbar і поле деталей були в одному `grid`-рядку | **Виправлено в r5:** scrollbar — рядок 1, деталі — 2, «Закрити» — 3; дані протоколів не змінені |
| Редактор інтервалу шайби | Була тільки команда «Зберегти» | **Додано «Скасувати» → тільки `w.destroy`** |

У редакторі інтервалу SQL `INSERT/UPDATE`, `commit` і `load_intervals` залишаються лише всередині явного callback `save`. «Скасувати» не викликає цей callback і не змінює інтервал. Окремого `WM_DELETE_WINDOW` для форми немає, тому штатний X закриває Toplevel без запуску збереження. Поведінковий Tk-тест перевіряє: введене, але не збережене значення після «Скасувати» або X не потрапляє в БД; modal grab звільняється; форму можна відкрити повторно; явне валідне «Зберегти» робить один запис, commit, refresh і закриває форму. Аналіз сканів, розпізнавання, протоколи та основний графік/табель у r5 не змінюються.

**Попередження імпорту відновлено:** стара логіка після невдалого пошуку кола підставляла `(0,0,0)`, а потім перевіряла `if not circles`, тому задумане повідомлення користувачу ставало недосяжним. r5 зберігає окремий прапорець `detected_circle` і реально показує попередження, що коло не знайдено.

**Імпорт більше не перезаписує старі результати:** раніше `import_scan()` після додавання нового файлу викликав `recognize_all()`, а той перед генерацією кандидатів видаляв усі наявні інтервали кожної шайби. Тепер імпорт і `seed_examples` викликають окремий `recognize_unprocessed(silent=True)`, який обробляє лише записи без жодного інтервалу (`NOT EXISTS`) і не містить `DELETE`. Уже перевірені/ручні інтервали залишаються недоторканими.

**Уточнено небезпечні дії:** кнопка `Видалити тест` була технічною/неясною назвою для фактичного видалення тахокарти — у r5 вона називається `Видалити тахокарту`. Видалення окремого інтервалу тепер вимагає явного підтвердження. Повторне розпізнавання вибраної тахокарти або всіх тахокарт перед `DELETE FROM intervals` попереджає, що поточні інтервали, включно з ручними правками, будуть замінені; відмова залишає БД без змін. Системний `silent=True` для тестового seed-сценарію не відкриває модальне підтвердження.

**Виявлена й виправлена проблема компонування:** у вікні протоколів горизонтальна прокрутка таблиці та текст деталей використовували один `grid(row=1)`, тому на частині розмірів/DPI могли накладатися. У r5 вони рознесені по окремих рядках, а кнопка «Закрити» перенесена нижче; regression перевіряє номери рядків і повторне відкриття без записів у БД.

**Виявлена й виправлена проблема даних:** ручний парсер часу раніше перевіряв тільки наявність `:` та чисел, тому, наприклад, `99:99` могло записатися в `start_min/end_min`, а відображення потім маскувало це через modulo 24 годин. У r5 ручне введення обмежене реальною добою `00:00–23:59`; невалідний час показує помилку до відкриття SQL-з'єднання.

**Автоматичний regression:** фіксує версію 10.17-r5; діапазон часу; окремі «Скасувати»/«Зберегти»; Cancel/X без запису; валідний Save із commit/refresh; звільнення modal grab і повторне відкриття; повторне відкриття статистичного Toplevel; розкладку й повторне відкриття протоколів; підтвердження видалення інтервалу; безпечне розпізнавання лише порожніх записів після імпорту; захист перед destructive re-recognition; зрозумілу назву видалення тахокарти; наявні «Закрити» у статистиці, скані й протоколах.

**Ще потребує ручного Windows UI smoke:** візуальне відчуття X / «Скасувати» / «Зберегти» з реальним введенням, 100/125/150 % DPI та доступність нижньої панелі кнопок. Автотест уже перевіряє відсутність неочікуваного запису й повторне відкриття, але не заміняє фізичну перевірку розмірів і фокуса. Попередження про втрату незбережених змін поки не додається вибірково: це має бути єдина UX-політика для всіх форм, а не особливість лише тахографа.

### Наступна група після r5
- Маршрути та решта діалогів Експлуатації: перевірка X/Скасувати/Зберегти й повторного входу.
- Реєстр працівників та інші таблиці: спільне сортування заголовків із коректними типами дат/чисел/тексту.

## Прохід r6 — Маршрути та залишковий діалог Експлуатації

**Маршрути — навігація та чернетка:** у головній картці маршруту, редакторі точки, редакторі частини зміни та обох формах швидкого вставлення додано явне non-saving **«Скасувати»**. Кнопка закриття графіка руху уточнена як **«Готово — повернутися до маршруту»**: зміни цього дочірнього вікна лишаються лише у чернетці батьківської картки і не пишуться в SQLite до явного «Зберегти маршрут». Стандартний X так само не викликає callback збереження.

**Локально руйнівні дії:** видалення точки з графіка руху та видалення частини маршруту тепер вимагають підтвердження. Це захищає від випадкової втрати уже введеної частини чернетки, хоча БД до фінального збереження маршруту не змінюється. «Вимкнути» маршрут і раніше мало окреме підтвердження та лишається деактивацією, а не фізичним видаленням.

**Сортування реєстру маршрутів:** усі 8 заголовків таблиці стали клікабельними через спільний type-aware `table_sorting.sort_treeview`. Повторний клік перемикає ▲/▼, вибір рядка та focus зберігаються. Після «Оновити» застосовується попереднє сортування і відновлюється вибраний маршрут за стабільним ID.

**Експлуатація:** статичний аудит підтвердив, що редактор наказу, закріплення, масове закріплення, учасники/ТЗ, preview і редактор тексту інструктажу вже мають «Скасувати»/«Закрити». Окреме вікно **«Історія наказу»** такого виходу не мало; у r6 додано «Закрити» → тільки `dlg.destroy`, без зміни історії чи БД.

**Не змінюється:** бізнес-логіка маршрутів/наказів, схема SQLite, plan/fact, шляхові листи, документи, backup, бібліотека шаблонів і сховище документів.

**Ручний gate залишається:** Windows 100/125/150 % DPI, фокус/табуляція, вкладені modal grab та візуальна доступність нижніх кнопок. Regression перевіряє структуру callbacks, сортування й destructive-confirmation, але не підміняє фізичний UI smoke.

### Наступна група після r6
- Реєстр працівників та інші таблиці: послідовно підключати спільне сортування з правильними типами дат/чисел/тексту.
- Продовжити інвентаризацію службових/налаштувальних Toplevel на вихід, X та побічне збереження.


## Прохід r7 — реєстр працівників і службові/налаштувальні вікна

**Реєстр працівників:** основна таблиця у workspace отримала клікабельне сортування всіх 8 колонок через спільний `table_sorting.sort_treeview`. Типи задані явно, а не вгадуються за відображеним текстом:

| Колонка | Тип сортування |
|---|---|
| Таб. № | текст із природним порядком |
| ПІБ | текст |
| Посада | текст |
| Спеціальні ролі | текст |
| Режим | текст |
| Норма/тиж. | тривалість `ГГ:ХХ` |
| Прийнятий | дата |
| Стан | статус: «Працює» → «Звільнений» |

Повторний клік по тому самому заголовку перемикає ▲/▼. Після `Оновити` і після зміни пошукового фільтра попереднє сортування застосовується повторно. Вибраний працівник зберігається за стабільним employee ID; якщо пошук тимчасово приховав рядок, ID пам'ятається і вибір відновлюється, коли рядок знову стає видимим.

**Сумісний старий реєстр працівників:** приведений до того самого контракту, щоб резервний/legacy шлях не поводився інакше. Для ID і окладу використовується числовий тип, для дат прийняття/звільнення — дата, для стану — статус; після reload зберігаються сортування та вибраний employee ID.

**Спільний sorter:** розширено без зміни старого контракту ТЗ/Маршрутів. Додано явні типи `number`, `date`, `duration`, `status`; виклики без `value_type` зберігають попередню поведінку `id/year/documents/text`. Сортування лише переставляє видимі рядки Treeview й не змінює БД, фільтри чи бізнес-статуси.

**Паралельний аудит службових/налаштувальних UI:**
- вкладка налаштувань Експлуатації не є окремим Toplevel: запис у БД знаходиться лише в callback явної кнопки **«Зберегти»**; перехід на іншу вкладку або закриття центру не викликає цей callback;
- **«Простий місячний графік роботи»** — single-instance Toplevel: має окрему **«Записати план»** та явне **«Закрити» → `win.destroy`**; спеціального `WM_DELETE_WINDOW`, який міг би викликати запис, немає. Після знищення повторний виклик створює нове вікно.

**Не змінюється:** SQLite schema, дані працівників, режими/табелі, накази, документи, backup, бібліотека шаблонів і сховище документів. r7 змінює лише сортування/відновлення UI-стану та regression-контракти.

**Ручний gate залишається:** фізично перевірити Windows 100/125/150 % DPI, фокус/табуляцію, поведінку X із реально введеними незбереженими значеннями та повторне відкриття. Статичний аудит і regression не підміняють цю перевірку.

### Наступна група після r7
- послідовно переносити type-aware сортування на інші робочі таблиці, починаючи з найбільш уживаних реєстрів, без масової одночасної зміни;
- продовжити аудит решти службових/налаштувальних Toplevel на явний вихід, X, незбережені дані, destructive actions і повторне відкриття.


## Прохід r8 — реєстр наказів, фільтр груп і службова історія

**Реєстр наказів Експлуатації:** сортуються кліком усі дев'ять колонок. `Дата` — дата (не лексикографічний текст); `№` — природний текст, щоб номер на кшталт `2-К` був перед `10-К`; `Серія`, `Група`, `Тип наказу`, `Тема` та `Контроль` — природний текст. `Стан` має явний порядок «Чернетка» → «Діє в Taxo» → «Скасовано», `Паперовий оригінал` — явний порядок «підписано» → «—». Другий клік перемикає ▲/▼; порожні значення залишаються в кінці в обох напрямках.

**Вибір і фільтр:** після refresh, редагування/підпису/затвердження чинне сортування не губиться. Вибраний наказ пам'ятається за `operations_orders.id`, а не за позицією у `Treeview`. Якщо фільтр груп приховав вибраний наказ, він не підмінюється іншим; коли фільтр повертає рядок — відновлюється попередній вибір. Після фізичного видалення наказу запам'ятований ID очищається, тому привид видаленого вибору не відновлюється. Це UI-стан; `ops.list_orders` і структура наказів незмінні.

**Доступність/руйнівні дії:** підтвердження перед «Ввести в дію в Taxo», «Скасувати наказ», «Видалити наказ» збережені. У головному центрі Експлуатації вже є явне «Закрити» (r2); дочірня «Історія наказу» має окреме «Закрити» → `dlg.destroy` (r6), без операцій UPDATE/DELETE. Налаштування нумерації знаходяться у вкладці того самого центру, без створення другого Toplevel.

**Не змінено:** права на редагування, погодження/скасування, історію, схему SQLite, робочі дані, рендер наказів, backups, бібліотеку шаблонів і сховище документів. Зміни зосереджені в `order_register_ui.py` та regression-gates.

**Потребує фізичного UI-приймання:** взаємодія заголовків зі scrollbar та контрастом ▲/▼, фокус і подвійний клік після сортування, X/повторне відкриття центру/історії, DPI 100/125/150 %. CI та статичний аудит не заміняють реальний Windows smoke.

### Наступна група після r8
- Продовжити за картою таблиць з датами/статусами — журнал історії наказів та інші робочі реєстри, по одному ізольованому кроку.
- Перевіряти службові Toplevel, незбережені дані, зрозумілий вихід і підтвердження перед destructive actions.


## Прохід r9 — реєстр водіїв і вихід із вікна пулів шляхівок

**Реєстр водіїв:** шість заголовків мають сортування кліком через спільний `table_sorting.sort_treeview`. Колонки `ID` — число, `ПІБ` і `Посвідчення` — природний текст, `Дата народження` і `Прийнятий з` — дата, `Статус` — заданий порядок «Так» → «Ні». Другий клік перемикає ▲/▼, порожні значення в кінці. Після «Оновити» зберігаються сортування та вибраний водій за стабільним `drivers.id`, а не за позицією рядка. Оновлення залежних списків для табеля/бланків залишається на старому місці.

**Реєстр пулів серій і номерів шляхівок (Toplevel):** старий напис «Закрити / активувати» помилково міг означати вихід із вікна. Дію зміни стану перейменовано на **«Деактивувати / активувати пул»**, а для виходу додано окрему **«Закрити вікно» → `win.destroy`**, яка нічого не записує. Default X, як і раніше, просто знищує вікно; повторний виклик створює нове, якщо старе знищено.

**Destructive/зберігання:** операції завершення ролі водія залишені без змін і надалі мають тристоронній вибір (реальне завершення, виправлення історичного помилкового призначення, скасування), валідацію дати, а потім явне збереження. Кнопка «Закрити вікно» не викликає `toggle_waybill_number_pool`.

**Не змінено:** SQL схему, ролі/історію водіїв, дані пулів, автонумерацію, план/факт, документи, backup, шаблони чи сховище документів. Нова логіка лише переставляє видимі рядки, без SQL UPDATE.

**Ручний gate:** перевірити драйверський Treeview після refresh і повернення фокуса, ▲/▼ на Windows 100/125/150 % DPI; нову «Закрити вікно» і X у маленькому viewport, доступність на 900×600, повторне відкриття після X. Це не замінюється CI.

### Наступна група після r9
- Перевірити й послідовно підключити сортування для інших робочих таблиць, зокрема журналу історії наказів, із типами дат/чисел/статусів;
- далі проходити решту Toplevel на явне закриття, X, незбережені зміни, destructive actions і повторний вхід.


## Прохід r10 — журнал історії наказів

- Журнал `Історія наказу` раніше показував останні до 500 записів у хронологічному порядку, але всі чотири заголовки були неклікабельні. Додано сортування `Коли` (повний datetime, а не лише дата), `Об'єкт`, `Дія`, `Примітка`; повторний клік перемикає ▲/▼. Порожні значення йдуть після заповнених, як і в інших реєстрах.
- Shared `table_sorting` отримав явний тип `datetime` для ISO-часу журналу з точністю до секунд та локального `ДД.ММ.РРРР ГГ:ХХ`. Наявні виклики сортування за `date`, `text`, `number`, `duration`, `status` не змінюються.
- Журнал залишається **read-only**: сортування переставляє тільки рядки `Treeview`, не виконує запис у БД, не змінює порядок зберігання подій, не редагує історію. Явна **«Закрити»** (додана r6) викликає тільки `dlg.destroy`; стандартний X так само не зберігає. Наступне відкриття знов читає історію з БД.
- Додано регресійні перевірки хронологічного сортування однієї дати з різним часом, спадного порядку, форматів часу, клікабельних чотирьох заголовків та відсутності записів із діалогу.
- Потрібен окремий ручний UI gate: Windows DPI 100/125/150 %, доступність горизонтального scrollbar, фокус, контраст ▲/▼, X і повторне відкриття.
- **Кожна п'ята ревізія — r5/r10:** за новим правилом власника r10 вважається тестовим випуском лише після фактичної публікації `GitHub Pre-release` з усіма portable assets. Зелений CI чи Actions artifacts самі по собі не замінюють release; `Stable/Latest` не змінюється.


## Прохід 10.18-r1 — таблиці військово-транспортного обліку ТЗ

- Після stable 10.17-r10 аудит продовжено з центру **«Військово-транспортний облік ТЗ»**. Головний Toplevel уже мав безпечний явний вихід «Закрити»; r1 змінює тільки поведінку п'яти видимих таблиць.
