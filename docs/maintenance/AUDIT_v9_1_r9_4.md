# Передетапний аудит — Taxo 9.1 candidate r9.4

**Дата:** 19.09.2026  
**Stable baseline:** Taxo 9.0.1  
**Candidate:** Taxo 9.1 candidate r9.4  
**Гілка:** `work/v9.1-monthly-dispatch-waybill-ui`  
**PR:** #29

## Висновок аудиту

r9.4 підготовлено як окрему стабілізаційну контрольну точку перед наступним етапом. Автоматичні source/regression тести проходять на Windows, macOS ARM64 і macOS Intel. Критичні знайдені під час аудиту проблеми виправлено.

**Stable main не змінювати до ручної перевірки на робочій базі.**

## 1. Аудит графіків водіїв

Колишню двозначну дію «Перевірити графіки» перероблено на окремий центр **«Аудит графіків…»**.

Перевіряються технічні помилки введення:
- перекриття робочих частин;
- перекриття інтервалів керування;
- неповні пари часу;
- керування поза межами робочого інтервалу;
- порожні часові частини;
- активні маршрути без часового сценарію;
- legacy worklog без work_segments, якщо точні часові поля збережені у самому worklog.

Області аудиту:
- поточний день;
- весь місяць;
- шаблони маршрутів;
- місяць + маршрути.

На добовому графіку тепер показується окремий стан:
- `⚠ день: N помилк.`;
- `✓ день: помилок введення немає`;
- `○ день: записів для аудиту немає`;
- `○ день: є запис, але точний час не задано`.

Це прибирає попередню неоднозначність, коли «нічого не знайдено» і «нічого не перевірено» виглядали однаково.

Нормативний контроль №340 навмисно не змішується з технічним аудитом. Перехід до №340 дозволений тільки для явно вибраної проблеми конкретного дня водія, щоб не відкрити аналіз випадково для раніше вибраного іншого водія.

## 2. Канонічні часові інтервали

Перевірено інваріанти r9/r9.1:
- exact work_segments мають пріоритет над збереженими агрегатами;
- перекриття рахуються як union інтервалів, без подвійного рахунку хвилин;
- реальний нічний перехід через 00:00 зберігається;
- перекриття одного дня не перетворюється на фальшивий перехід на наступну добу;
- нові перекриття блокуються у дні, маршруті та копіюванні;
- старі конфлікти не переписуються автоматично;
- duration-only значення не породжують вигаданого 08:00–16:00.

## 3. Персонал і П-5

Перевірено:
- нові поля П-5 додаються до існуючої БД адитивно;
- факт має пріоритет над планом;
- якщо план існує, а факту немає, рішення про підстановку приймає користувач перед формуванням;
- підставлений план не маскується: клітинки виділяються і документ отримує явну примітку;
- надурочні, нічні, вечірні та вихідні/святкові години зберігаються окремими фактичними категоріями;
- відсутність не видаляє історичний графік.

## 4. Дані та міграції

Під час аудиту перевірено схему та міграційні ділянки.

Підтверджено:
- r9.4 не використовує DROP TABLE / DROP COLUMN для міграції робочої БД;
- нові поля додаються через контрольовані ALTER TABLE ADD COLUMN;
- SQLite foreign_keys увімкнено;
- робоче сховище відокремлене від каталогу програми;
- тахографічна БД зберігається окремо від основної;
- юридичний архів бланків не очищається автоматично;
- робочий табель автоматично тримає 48-місячне вікно відповідно до поточної вимоги проєкту.

### Резервування

Підтверджено:
- автоматична SQLite backup-копія не частіше одного разу на добу;
- зберігаються останні 30 резервних копій;
- ручна резервна копія доступна з UI;
- перед відновленням створюється страхова копія поточної БД;
- файл відновлення перевіряється через SQLite `quick_check`;
- відновлення виконується через тимчасову БД та атомарну заміну;
- робоче сховище має механізм блокування від одночасного штатного відкриття двома сучасними копіями Taxo.

## 5. Архів підтверджень діяльності

Перевірена логіка r9.3:
- новіші бланки сортуються зверху;
- є фільтр за поточно вибраним водієм;
- є опційний місяць/рік;
- фільтри можна скинути;
- фільтрація не змінює самі архівні записи;
- редагування працює за ID вибраного запису, а не за позицією у повному списку.

## 6. Місячний контроль

Перевірена структура:
- компактні місячні показники;
- вкладка «Дні місяця»;
- окремий «Контроль №340»;
- перехід до конкретного дня для редагування;
- окрема команда «Відкрити деталізацію».

Технічний аудит графіка і нормативний аналіз №340 залишаються двома різними функціями.

## 7. Build / CI / release safety

Під час аудиту знайдено і виправлено дві причини червоних CI:
1. старий тест v8.70 очікував історичні назви артефактів r11, хоча workflow вже формує назви r9.4;
2. fixture нового тесту аудиту очікував два активні маршрути, але створював лише один.

Після виправлення:
- **Windows:** 97 unittest — success;
- **macOS ARM64:** 97 unittest — success;
- **macOS Intel x86_64:** 97 unittest — success;
- START/source package workflow — success.

Додатково:
- `.gitignore` доповнено шаблонами артефактів Taxo 9.1, щоб ZIP/Setup/checksum випадково не потрапляли в Git;
- historical publisher r7 і r8 переведено у manual-only режим;
- historical publisher r7/r8 pinned до власного tag;
- повторний запуск r7/r8 тепер відмовляється перезаписувати існуючі release assets;
- r9.1/r9.2/r9.3 уже використовують immutable release policy;
- попередні candidate tags не пересуваються.

## 8. Версійна узгодженість

Перевірено r9.4 у:
- `VERSION.txt`;
- `taxo_app.py`;
- `v91_features.py`;
- `personnel_v91.py`;
- `Taxo.spec`;
- `Taxo_macos.spec`;
- `BUILD_WINDOWS.bat`;
- `BUILD_MACOS.sh`;
- `BUILD_INSTALLER.bat`;
- `installer/Taxo.iss`;
- поточних Windows/macOS workflow artifact names;
- release notes і maintenance documentation.

Файли workflows історично мають назви `build-*-v8.70.yml`, але їхня поточна назва job та артефакти вже описують Taxo 9.x. Перейменування самих workflow-файлів перед r9.4 не робиться, щоб не створювати зайвий release/CI churn.

## 9. Що не автоматизується навмисно

Не виконувати автоматично:
- виправлення старих графіків із конфліктами;
- підстановку плану замість факту у П-5 без рішення користувача;
- merge candidate у main;
- визначення нормативного порушення №340 лише з факту технічної помилки введення.

## 10. Ручна експлуатаційна перевірка перед наступним етапом

Після публікації r9.4 перевірити на робочій Windows-базі:

1. «Аудит графіків…» для поточного дня без записів, чистого дня і дня з реальною старою помилкою.
2. Весь місяць і шаблони маршрутів, включно з опцією неактивних маршрутів.
3. Подвійний клік → виправлення дня/маршруту → повторний аудит.
4. Окремий перехід з проблемного дня у «Контроль №340».
5. Нічна зміна через 00:00 та розділена зміна.
6. Відпустка/лікарняний: Персонал → табель водія → баланс → П-5.
7. П-5 у двох режимах: тільки факт / підтверджена підстановка плану.
8. PDF та Excel П-5: читабельність на A4 і примітка про підставлений план.
9. Архів бланків: поточний водій, місяць, скидання фільтрів, новіші зверху.
10. Місячний контроль: таблиця днів, редагування та «Відкрити деталізацію».
11. Резервна копія → перевірка файла → тестове відновлення на копії робочого сховища.
12. Запуск через START.bat на робочому Windows.
