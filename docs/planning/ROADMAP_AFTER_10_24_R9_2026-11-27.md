# Taxo — план розвитку після Stable 10.24-r9

**Дата фіксації:** 27.11.2026  
**База:** Stable/Latest `v10.24-r9`, exact product source `e3770aa72b0744eee192979a2e569651bac4f257`.  
**Принцип:** рухатися змістовними блоками. Не створювати ревізію заради однієї дрібної кнопки. Після кожного блоку: ізольований synthetic workspace → regression → multi-platform CI → Test release → ручне приймання власником → лише потім Stable за прямим рішенням.

## Етап 1 — 10.24-r10: закрити контур «Накази / Учасники / ТЗ»

Мета — не додати нову бізнес-функцію, а довести вже створений механізм як один завершений цикл.

### 1.1. Наскрізний сценарій на ізольованому workspace
Перевірити без робочої бази власника:
1. створення звичайного наказу;
2. додавання кількох працівників і ТЗ;
3. редагування ролі/примітки без переписування frozen identity snapshot;
4. видалення та повторне додавання учасника;
5. створення наказу про закріплення водій–ТЗ;
6. одиночне й масове додавання пар;
7. редагування пари;
8. видалення та повторне додавання;
9. закриття SQLite і повторне відкриття;
10. переведення наказу «Чернетка → Діє в Taxo» без втрати учасників/пар;
11. Preview з актуальних persisted даних;
12. формування DOCX/PDF/JPG;
13. однакові ключові реквізити в Preview/DOCX/PDF;
14. full backup з Output;
15. restore у новий порожній workspace;
16. повторне відкриття наказу, учасників, пар і готових файлів після restore;
17. побайтове порівняння відновлених готових файлів.

### 1.2. UI-приймання
Автоматичний тест не заміняє ручне приймання. Перед закриттям #553 перевірити в реальному вікні:
- наказ зі списку → «Учасники / ТЗ»;
- тема/номер/дата/стан однозначно показані;
- багатовибір працівників і ТЗ;
- вибір не губиться при пошуку;
- роль/примітка редагуються;
- пари водій–ТЗ редагуються без переходу у незрозуміле стороннє вікно;
- повторне відкриття не губить дані;
- DOCX/PDF/JPG зрозуміло відповідають наказу;
- X / Скасувати / Закрити не гублять незбережене мовчки;
- внутрішня область «Документи» має робочий splitter і не ховає дії на малому вікні.

### 1.3. Критерій завершення r10
- немає нового підтвердженого дефекту в наскрізному сценарії;
- synthetic end-to-end gate PASS;
- старі r7/r8 guards залишаються PASS;
- START, Windows, Windows 7, macOS Intel/ARM PASS;
- Defender/integrity PASS;
- Test release `v10.24-r10`;
- #553 не закривати до ручного owner acceptance;
- #562 закривати лише після ручної перевірки splitter;
- широкий #556 лишається відкритим, доки не пройдено весь UI-аудит B/C.

## Етап 2 — лінія 10.25: Інструктажі БДР / охорона праці / стажування

Основа — Issue #237. Паперовий журнал і власноручний підпис залишаються юридичним/фактичним підтвердженням; Taxo не вигадує «проведено» з факту друку.

### 2.1. Дані
- програма/шаблон: напрям, вид, редакція, чинність від/до, локальна підстава, затвердив;
- правило планування: категорія працівників/робіт, періодичність або подієвий тригер;
- плановий захід: період, цільова група, програма, строк;
- позаплановий захід: подія/підстава, дата, працівники;
- факт: окрема ручна відмітка відповідального, дата, посилання на паперовий запис/скан за наявності;
- історія редакцій не переписується.

### 2.2. UI
Два основні входи:
- **«На цей квартал»** — що треба підготувати, кому, до якої дати, що прострочено;
- **«За подією»** — окремий позаплановий інструктаж.

Потрібні:
- вибір груп/працівників із єдиної бази;
- масова підготовка комплектів;
- відкриття програми;
- лист підписів;
- друкований текст;
- зрозумілий статус «підготовлено / строк настав / прострочено / факт підтверджено вручну»;
- позаплановий не закриває плановий автоматично.

### 2.3. Надійність
- один плановий захід не дублюється повторним натисканням;
- зміна програми створює нову редакцію;
- backup/restore зберігає плани, програми, створені документи й скани;
- synthetic tests для 1/багатьох працівників, зміни програми, строків, події, restore.

## Етап 3 — єдине сховище документів

Основа — #289 і наявні Document Catalog / Document Vault / PaperDocuments / order sources.

### 3.1. Єдина модель пошуку, не нова копія всього
Каталог індексує наявні джерела:
- накази;
- інструктажі/стажування;
- кореспонденцію;
- документи працівників;
- документи ТЗ;
- підготовлені власні документи.

Фізичні байти не дублювати без причини.

### 3.2. Обов'язкові можливості
- пошук;
- дата від/до;
- тип/напрям;
- номер/тема;
- працівник/ТЗ;
- дерево «за видами / за датами / мої папки»;
- готовий файл Taxo;
- окрема ознака паперового оригіналу;
- добровільний скан;
- заміна скана з історією;
- відкриття пов'язаного об'єкта;
- перевірений full backup/restore.

### 3.3. AI-ready структура
Для кожного документа зберігати машинно зрозумілі метадані: вид, дата, номер, сторони/сутності, джерело, зв'язки, статус файла, hash/size, provenance. Це дозволяє надалі безпечно сортувати існуючу базу ШІ, не вгадуючи по назві файла.

OCR/AI APPLY не вмикати автоматично; спочатку read-only proposal/review.

## Етап 4 — СТОІР як окрема функціональна область

Не змішувати з наказами/інструктажами.

### 4.1. Спочатку інвентаризація наявного
Звірити:
- профілі ТО;
- події;
- заявки;
- пробіг/одометр;
- прогноз;
- строки;
- зв'язок із конкретним ТЗ;
- що входить у backup/restore.

### 4.2. Далі розвиток
- план ТО за пробігом/датою;
- заявка на ремонт;
- виконана робота;
- акт ТО/ремонту;
- історія ТЗ;
- контроль простроченого;
- документи робіт у спільному каталозі.
