# Аудит контракту бібліотеки після r5 — 13.11.2026

**Статус:** перевірка документації й коду **читання**, без редагування вже виданого кандидата r5 та без зміни Stable.  
**Перевірений r5 head:** `7ee89f3f0dcb731c4b2fd416b6ddb630e3ebe7d2`, [PR #396](https://github.com/RomanZavadaM/Taxo/pull/396).  
**Передумова:** `v10.18-r5` ще не опубліковано як GitHub Pre-release на момент цієї перевірки. Новий код r6 не починати до завершення обов'язкового release checkpoint.

## Що справді перевірено

Звірено `src/taxo/template_library_reader.py` на r5, `docs/planning/template_import_schema_v1.json` на main, маніфест бібліотеки v1 та план інтеграції r6. Читач r5 проходив 1242 source-тести та CI Windows, Win7, macOS Intel/ARM, проте тести **не означають повної валідації стороннього пакета**.

## Виявлені відмінності

| Знайдено | Ризик / наслідок | Рішення для наступної кодової ревізії |
|---|---|---|
| Маніфест v1 раніше дозволяв будь-який `category_id` відповідного шаблону; reader r5 дозволяє тільки шість категорій | Схемно правильний пакет міг отримати `DAMAGED` | **Виправлено схему**: enum збігається з reader |
| Маніфест не обмежував кількість `items/files`; reader має `MAX_FILES=2000` | Пакет проходив структурну схему, але не читач | **Виправлено схему**: `maxItems=2000` |
| Початковий `relativeFilePath` дозволяв надто вільні сегменти | Різниця між schema й `_safe_path`, складні небезпечні імена | **Виправлено схему**: кожен сегмент починається з літери/цифри/`_`/`-`; перевірено типові `../`, абсолютний/Windows шлях та приховані сегменти |
| Reader вручну перевіряє лише підмножину JSON Schema окремого шаблону | Зайві/невідомі поля, типи окремих полів, вміст таблиць та необмежені довгі рядки можуть пройти часткову перевірку | До імпорту/генерації потрібна **повна схема або еквівалентні конкретні валідатори**, із синтетичними негативними тестами |
| Reader рахує SHA-256 і розмір **заявлених** файлів | Це **не** гарантує, що в директорії немає незареєстрованого файла; SHA-256 не підтверджує постачальника | Інсталятор має вимагати точний набір файлів, без додаткових виконуваних/невідомих об'єктів, і окремий trust mechanism |
| Reader читає кожен файл до `MAX_TOTAL_BYTES=512 MiB` у пам'ять | Пакет з великими вкладеннями може спричинити зайвий піковий RAM; ZIP bomb / archive traversal у reader не перевіряється, бо reader взагалі не розпаковує ZIP | Сканувати великі файли streaming hash, ZIP розпаковувати лише в іншому майбутньому bounded installer |
| Вкладені `blocks.children` проходять рекурсивний обхід | Надто глибокі об'єкти/велика кількість блоків можуть спричинити recursion/resource errors | Обмежити максимальну глибину та кількість блоків, перетворювати помилки на зрозумілий `DAMAGED`, тестувати глибокі synthetic trees |
| Reader не має публічного `get_revision` з повним вмістом | `AVAILABLE` поки дає тільки список `TemplateSummary`; редактор/генерація недоступні | У майбутньому додати окремий метод отримання конкретної **перевіреної** редакції, не обіцяти цю можливість у r5/r6 UI |
| Розміщення за замовчуванням: `workspace/TemplateLibrary`; reader приймає явний Path | Користувацький override ще ніде не зберігається й не переміщується | Пропонований UI r6 спершу read-only; налаштування і двофазне переміщення окремим кроком |
| Поточні `Data/PaperDocuments`, `operations_orders`, `document_catalog` уже існують | Ризик другого незалежного архіву готових документів | Не дублювати каталоги і БД: інтегрувати наступний `DocumentVault` в існуючу картотеку через адаптер |
| Існуючий `template_import_schema_v1.json` забороняє `status`, окрім `proposed` | Не можна видавати vendor-item за затверджений підприємством документ | Зберігати approval в company revision і журнал рішень, а не у vendor item |

## Перевірки для майбутнього r6/r7

1. Позитивний синтетичний мінімальний каталог, а також бібліотека з сотнями дрібних шаблонів.
2. Негативні форми: зайві поля у manifest/item/template, відсутні обов'язкові поля, `items`/file-count 2001, невідома категорія, подвійні ID/path.
3. Path traversal (`../`, `C:\\`, абсолютний шлях), symlinks, case-insensitive collisions на Windows, dot-prefixed сегменти.
4. Той самий `revision_id` із зміненими байтами в новому пакеті має бути конфліктом.
5. Усі посилання на resources/annexes повинні вести на існуючі перевірені `files[]`.
6. Вкладені блоки: обмеження кількості/глибини, незнайомі `visible_when`, помилкові дані таблиць/змінних.
7. Missing root/manifest і тимчасово недоступний мережевий диск відображати окремими станами, без створення нової порожньої бібліотеки на місці пропалої.
8. Повна відсутність побічного запису в робочий `workspace` під час read-only перегляду.
9. UI відсутньої бібліотеки — зрозуміле повідомлення без відмови всього Taxo; закриття X і повторне відкриття.
10. Не показувати «встановлення/створення наказу/затверджено», поки цих функцій не існує.

## Архітектурне правило для всіх наступних змін

**Один ризик — один невеликий кодовий slice.** Не поєднувати в одній ревізії ZIP-інсталятор, редактор великих документів, міграцію `PaperDocuments` і нове UI. `main.py` тільки делегує; пояснення модулів, контрактів і повідомлень про помилки — у коді й проєктній документації. Заборонено залучати реальні документи/підписи до публічного GitHub та CI.
