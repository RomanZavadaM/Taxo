## Що перевірити незалежно

1. **Точки концентрації коду.** Реальний розмір/кількість функцій, класи, nested callbacks, дублікати, глобальний стан. Мінімум: `main.py`, `personnel_v91.py`, `operations_orders_ui.py`, `tachograph.py`, `operations_orders.py`, `safety_templates.py`.
2. **Фактичні зв'язки.** Ланцюжок запуску і `v10xx_features`, підміни/обгортки UI callbacks, імпорти, DB transactions, залежності `ApplicationServices`, `DataAccess`, `workspace`. Які модулі є справжніми доменами, а які — лише іншою назвою моноліту.
3. **Цілісність сценаріїв.** Масові пари водій–ТЗ у наказі, збереження/перегляд/друк документів, графіки й табелі, праця/відпочинок, персонал/ролі, транспорт/СТОІР, тахограф, інструктаж/стажування. Де код може існувати, але кнопка або результат користувачу недоступні.
4. **Дані та сумісність.** Workspace, SQLite/версії схем, історія кадрових/транспортних даних, збережені документи і вкладення, backup/restore, старі робочі сховища; ризики великих переміщень файлів.
5. **Збірки.** Windows 10/11, Windows 7 Python 3.8, macOS Intel/ARM, START, spec/config, специфічні залежності і обмеження на нові бібліотеки.
6. **Майбутні потреби.** Каталог готових документів (кадрові, виробничі, ОП, БДР; дата/працівник/ТЗ; опційні скани), збільшення числа модулів, можливість нових видів наказів, інструктажів, звітів та інфраструктури без подальшого розростання `main.py`.
7. **Альтернативна архітектура.** Чи достатньо поточних ідей доменних модулів? Які складові краще винести великими блоками, які не можна відділяти одночасно, як зафіксувати контракти і відмовитися від шару історичних обгорток без втрати поведінки.
8. **Контроль якості.** Чого бракує в Feature Loss Guard, чим підтверджувати правильність не лише на рівні методів, а сценаріями «створити → зберегти → відкрити → змінити → друк → резервна копія → відновлення»?

## Вимоги до результату

- **Порівняльний висновок:** ризики наявного стану, недоліки нашого плану та власна альтернативна пропозиція (за потреби).
- **Карта меж/залежностей:** не лише список файлів, а ключові групи та напрямки зв'язків.
- **Ризики за пріоритетом:** критично / суттєво / можна відкласти; підтверджений кодом доказ, а не припущення.
- **План переходу:** без переписування всього одразу, але з реальними великими доменними переміщеннями; для кожного етапу — мета, зміст, межа, rollback, критерії готовності, незалежні тести.
- **Питання власнику:** тільки ті рішення про майбутні бізнес-вимоги, яких не можна вивести з коду/документації.
- **Заборона хибного PASS:** окремо розділити «перевірено в коді», «перевірено автоматичними тестами», «потребує ручної перевірки власника».

**Після звіту:** власник і команда Taxo звірять незалежні висновки з Issue #290, остаточно оберуть структуру, і **лише тоді** розпочнуть нову кодову ревізію перебудови. Аудитор не вносить своїх правок.
