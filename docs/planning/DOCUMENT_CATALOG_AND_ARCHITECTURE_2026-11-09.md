# Наступний розвиток після 10.15-r2 — документи, інструктажі та архітектура

**Дата:** 09.11.2026  
**База:** Taxo 10.15-r2, exact main `a5c09ffefde06074dd5339386e8d7fef75581211`.

## 1. Що вже є

10.15-r2 дає:
- типові тексти інструктажів БДР і ОП;
- сезонні автобусні програми;
- готові тексти наказів;
- редагування перед друком/збереженням;
- паперову модель підтвердження: Taxo готує, але не вдає, що документ підписаний.

## 2. Наступний функціональний шар — каталог документів (#289)

### Завдання користувача

Через довгий час потрібно швидко відповісти:
- який документ оформляли;
- коли;
- по якому напряму;
- кого/якого ТЗ стосувався;
- де сформований файл;
- чи є паперовий оригінал;
- чи прикріплено його скан.

### Модель

Один запис каталогу не дорівнює скану.

Запис може мати:
- системний тип документа;
- дату;
- номер;
- тему;
- напрям;
- пов'язаний наказ/інструктаж;
- пов'язаних працівників/ТЗ;
- шлях/ідентифікатор створеного Taxo файла;
- допоміжну позначку про паперовий оригінал;
- 0..N прикріплених цифрових копій/сканів.

Скан:
- **необов'язковий**;
- PDF/JPG/PNG;
- копіюється у workspace, а не лишається випадковим зовнішнім шляхом;
- входить у full backup/restore;
- може бути замінений або видалений користувачем;
- не перетворює запис автоматично на «підписано».

### UX

Один екран «Документи», а не окремий архів для кожного модуля.

Фільтри:
- від / до;
- напрям;
- тип;
- номер/тема;
- працівник;
- ТЗ;
- є/немає скана.

Основні дії:
- відкрити документ Taxo;
- відкрити пов'язаний наказ/інструктаж;
- додати/замінити/видалити скан;
- відкрити скан;
- переглянути історію.

## 3. Інструктажі — наступний шар після готових текстів (#237)

Після бібліотеки програм потрібне робоче планування:
- «На цей квартал»;
- «За подією»;
- регулярні й позапланові не змішуються;
- список кого треба підготувати;
- строки;
- прострочені/пропущені;
- історія редакцій програми;
- друк списків без автоматичного «проведено».

Каталог #289 повинен бути спільним результатом і для цих документів.

## 4. Архітектурна межа (#290)

Фактичні найбільші файли main на 09.11.2026:
- `main.py` — ~848 КБ;
- `personnel_v91.py` — ~194 КБ;
- `operations_orders_ui.py` — ~84 КБ;
- `tachograph.py` — ~68 КБ;
- `safety_templates.py` — ~59 КБ;
- `operations_orders.py` — ~56 КБ.

### Нове правило розробки

**Не додавати новий домен у великий моноліт лише тому, що там уже є кнопка/вікно.**

Новий каталог документів одразу розділити щонайменше на:
- модель/сховище;
- роботу з вкладеннями;
- запити/фільтри;
- UI;
- інтеграційні адаптери до наказів/інструктажів;
- backup contract.

`main.py` лише підключає цей домен.

## 5. Як боротися з монолітами без ризику

Не робити великого переписування.

Для кожного винесення:
1. зафіксувати поточну поведінку regression test;
2. визначити маленьку межу;
3. перенести код без нової функції;
4. пройти повний regression;
5. звірити Feature Loss routes;
6. лише після цього наступне винесення.

Перші кандидати:
1. новий document catalog — одразу правильно;
2. `operations_orders_ui.py` — відокремити редактор наказу / assignment UI / preview-actions;
3. `personnel_v91.py` — дробити при наступних змінах персоналу;
4. `tachograph.py` — розділити import/analysis/protocol/UI;
5. поступово зменшувати `main.py`.

## 6. Рекомендована послідовність ревізій

Після ручного приймання 10.15-r2:

**Перший наступний slice:** read-only architecture inventory + автоматичний size/report guard без зміни бізнес-поведінки.

Після нього:
- фундамент каталогу документів (#289) як окремий модуль;
- інтеграція наказів та інструктажів у каталог;
- далі календар/контроль інструктажів (#237);
- паралельно дрібні extraction-кроки #290 лише там, де є повний regression.

Не змішувати в одній ревізії:
- нову бізнес-функцію;
- великий перенос старого коду;
- зміну схеми даних іншого домену.
