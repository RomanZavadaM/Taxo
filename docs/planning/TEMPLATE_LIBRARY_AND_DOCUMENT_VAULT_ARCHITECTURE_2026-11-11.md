# Taxo: єдина система шаблонів і архіву документів

Дата: 11.11.2026. Стан: **архітектурний проєкт, не реалізований код**. Основа: stable v10.16-r8. Цей документ не змінює робочих даних, схему БД чи реліз.

## 1. Дві різні системи під одним інтерфейсом

**А. Бібліотека шаблонів** — користувацькі зразки, які можна створювати, копіювати, редагувати, імпортувати/експортувати, архівувати. Початкові шаблони Taxo — лише приклади; оновлення програми не перезаписує правки. Шаблон не є наказом і не має факту підписання.

**Б. Архів документів** — конкретні накази, інструктажі, інструкції, програми, протоколи, акти, журнальні листи, додатки. Документ може бути створений за шаблоном, вручну або імпортований. Кожен має незмінну історію редакцій та опційні вкладення (створені DOCX/PDF, паперовий скан, власне підписаний електронний файл, файл відокремленого КЕП). Зміна шаблону не переписує документ.

**В. Зв'язки** — документ посилається на версію шаблону й відповідний наказ/працівника/автомобіль/інструктаж/стажування. Зв'язок не замінює основний реєстр наказів.

## 2. Що зберегти з наявного Taxo

Зараз існують `Data/PaperDocuments/index.json` з підготовленими DOCX та інформаційною ознакою `paper_signed`; `operations_orders` у `Data/driver_worktime.sqlite3`; read-only об'єднання у `document_catalog.py`; `Data/EmployeeDocuments` і `Data/VehicleDocuments`; `Output` для експортів. Вони не видаляються й не переписуються «міграцією заради чистоти». Новий архів — обліковий шар, що індексує наявні об'єкти, а не ще один незалежний реєстр наказів.

Не зберігати документи й бібліотеку в каталозі встановленої програми. Зберігати у вибраному робочому сховищі Taxo; не включати робочі документи користувача до GitHub, тестових архівів чи інсталяторів.

## 3. Запропонована структура робочого сховища

```text
<WORKSPACE>/
  Data/
    driver_worktime.sqlite3           # чинна БД + нові таблиці метаданих
    PaperDocuments/                  # наявні DOCX та index.json (legacy)
    EmployeeDocuments/               # наявні
    VehicleDocuments/                # наявні
    DocumentVault/                   # нове кероване сховище
      objects/
        ab/
          <file-id>.<ext>             # машинні імена, незмінні байти
      staging/                        # тимчасово, контрольовано видаляти
      quarantine/                     # відхилені/пошкоджені файли
  Output/                             # експорти; не головний архів
  Backups/
```

Файли зберігаються окремо від SQLite; БД зберігає лише UUID, тип, роль, розмір, SHA-256, відносний storage key, зв'язки. Ніколи не приймати довільні абсолютні або `../` шляхи. Не довіряти символічним посиланням. Атомарне завантаження: staging → перевірка типу/розміру/hash → запис → транзакція БД; crash-recovery із журналом staging. Пошук за назвою, датою, видом, номером, працівником, ТЗ, змістом (за умови індексації), станом і вкладеннями.

## 4. Модель даних (пропозиція для окремої міграції)

**Шаблони**
- `template_libraries`: UUID, owner_scope (personal/company/system), owner_user_id або профіль, company_id, назва, archived_at.
- `templates`: UUID, library_id, kind, scenario, title, description, active_revision_id, status.
- `template_revisions`: UUID, template_id, revision_no, schema_version, content_json, content_hash, created_at, created_by, immutable=true.
- `template_sources`: template_id, archival source IDs, коментарі, review_status, без збереження приватних архівів у репозиторії.

**Документи**
- `vault_documents`: UUID, kind, title, date, number, source_kind/source_id (order, briefing, internship, manual, imported), template_revision_id nullable, company_id, status, created_at, created_by.
- `vault_document_revisions`: UUID, document_id, revision_no, filled_content_json / immutable snapshot, created_at, reason.
- `vault_files`: UUID, document_id, revision_id nullable, role, mime, original_filename, storage_key, sha256, size_bytes, source, created_at, supersedes_file_id nullable.
- `vault_links`: document_id, entity_kind, entity_id (employee, vehicle, order, instruction, internship, work_schedule, other).
- `vault_signature_evidence`: UUID, file_id, signature_file_id nullable, signature_type, verification_state, verifier, verified_at, certificate_summary, signed_bytes_sha256, verification_report, checked_offline_at nullable.
- `vault_audit_events`: UUID, event, actor, timestamp, document_id, before/after record pointers, без персонального вмісту в plain logs.

Не вимагати фізичного входу/ролі користувача, доки не перевірено наявну модель акаунтів; власна бібліотека за профілем і спільна корпоративна — різні області. Не заявляти про ізоляцію прав, якої Taxo не має.

## 5. Повноцінні довгі тексти: інструктажі, програми, інструкції

**Жодного ліміту «кілька рядків», фіксованих 3 пунктів чи одного короткого `body`.** Зберігати документ як послідовність довільної кількості структурних блоків. Розділи можуть вкладатися: частина → розділ → пункт → підпункт. Блоки: `heading`, `paragraph`, `numbered_list`, `bullet_list`, `table`, `page_break`, `figure`, `attachment_reference`, `signature_placeholder`, `dynamic_table`. Підтримувати багатосторінкові тексти, програми на десятки сторінок, гриф затвердження, інструкції з багатьма пунктами, тематичні плани та журнальні листи.

**Зберігати і смислову структуру, і оригінальне оформлення.** Редакція шаблону містить versioned `content_json` з блоками та `variables`; за потреби окремо зберігати оригінальний DOCX/ODT/PDF як reference/source attachment. Імпорт DOCX має показувати попередній перегляд і втрати оформлення перед перетворенням, а не обіцяти ідеальне round-trip. Скановані PDF/зображення можуть не мати тексту; OCR лише опційний з перевіркою людиною, оригінальні байти недоторканні.

**Редактор:** навігація по розділах, згортання, пошук і заміна, нумерація/багаторівневі списки, великі таблиці, стилі заголовків, вставляння розривів сторінок і змінних, історія редакцій, чернетка з автозбереженням і явним затвердженням нової редакції шаблону. Відкладене завантаження довгих розділів і фонова індексація змісту, без блокування UI. Не завантажувати весь DOCX у Tk.Text одним неструктурованим рядком.

**Змінні:** допустимі `company.name`, `order.number`, `order.date`, `employee.*`, `vehicle.*`, `training.topic`, `training.program_sections`, `training.participants`, `assignment.pairs` та інші затверджені іменовані поля. Відомості беруться з реальних сутностей Taxo або вводяться користувачем. Ніякого `eval`, Python, SQL, макросів чи довільних шляхів у шаблонах. Незаповнені критичні змінні — помилка перед випуском.

**Повторне використання:** для 30-сторінкової інструкції користувач змінює лише потрібний розділ, створюється нова редакція шаблону; старі документи та попередні версії програми інструктажу залишаються відтворюваними. Для наказу про закріплення короткий текст плюс таблиця реальних пар — достатньо, якщо відсутні інші фактичні підстави.

**Обмеження безпеки й продуктивності:** зберігати UTF-8 Unicode; документ може бути великим, не обрізати вміст. Мати configurable технічні межі за розміром окремого вкладення/пакета для захисту від ресурсного виснаження, а не обмеження «кілька сторінок». Streaming/hash файлів і посторінковий preview/print; великі файли не читати цілком у пам'ять. Перевірки 1/10/50/100+ сторінок, довгі таблиці, кирилиця, багаторівневі списки, різні шрифти, Windows/Win7/macOS; без тихого усічення.

## 6. Типи файлів та доказ підписання

Ролі вкладень: `generated_editable` (DOCX/ODT), `generated_view` (PDF/JPG), `paper_scan` (PDF/JPG/TIFF), `signed_original` (PDF з вбудованим підписом, DOCX або інший формат), `detached_signature` (наприклад .p7s/.sig), `annex`, `source_reference`, `verification_report`. Окремі ролі, тому DOCX з текстом не підміняє підписаний оригінал.

- **Без скану/КЕП:** документ існує, архів не показує «підписано».
- **Скан паперового оригіналу:** користувач добровільно додає файл. Показувати `Скан додано — підпис не перевірено` або окрему вручну підтверджену паперову ознаку. Скан — зображення підпису, не КЕП.
- **КЕП/PAdES/CAdES/ASiC чи інша форма електронного підпису:** зберігати *точні оригінальні байти* файлу й відокремлений файл підпису, якщо він є; зв'язати через SHA256. Перевірка має використовувати надійний сумісний валідатор (окремий майбутній модуль); поки такого немає — `not_verified`, не `valid`.
- Після реальної перевірки зберігати час, засіб перевірки, результат, дані сертифіката й статус на момент перевірки; підписані байти ніколи не редагувати «на місці». Перевірити, чи підпис покриває саме цей файл, а не просто існує поруч. Не зберігати приватні ключі користувачів у Taxo.
- Стани документів окремо від станів файлів: `draft/prepared/issued/archived/superseded`; наявність скану не перемикає `issued` автоматично. Типове право ухвалювати рішення про чинність не виводиться з шаблону або скану.

## 7. Надійність, резервування, сумісність

- Для справді **повної** backup-копії за замовчуванням включати SQLite + user template revisions + усі обов'язкові `DocumentVault/objects` + `PaperDocuments` + `EmployeeDocuments`. Якщо користувач відключив великі вкладення, результат називати «неповна резервна копія» й показувати відсутні категорії до створення. `VehicleDocuments/TachographScans/Output` дотримуються існуючих явних опцій, доки окремо не узгоджено інше.
- Маніфест містить `vault_objects_included`, count, total_bytes і hashes; відновлення перевіряє DB integrity, checksum кожного файлу, відсутність orphan/пошкоджених зв'язків. Без тихої втрати паперових сканів чи підписів.
- Міграція зі старого `PaperDocuments/index.json` має підтримувати читання старих записів і нових поруч. Ідемпотентний імпорт з `legacy_source` та `legacy_id`, без дублювань і модифікації старих файлів.
- Для мережевого workspace враховувати блокування та атомарність. Контроль гонок на шаблонах (optimistic revision), дублікати й зміни паралельних користувачів; не перезаписувати чужу редакцію.
- Документ або шаблон можна експортувати окремо в portable package; імпорт не змінює робочі накази до preview/підтвердження. Неперевірені вхідні файли не виконувати і не відкривати автоматично.

## 8. UI і взаємодія

**«Шаблони»**: Мої / підприємства / початкові; тип → сценарій → шаблон → редакції → створити конкретний документ. Дії: редагувати, зберегти як, архівувати, імпорт/експорт. Окрема розгорнута редакторська форма для довгих текстів із деревом розділів.

**«Документи»**: єдиний пошук по наказах, інструктажах, стажуваннях і вкладених документах; картка має `Зміст / Історія / Файли / Підписи / Зв'язки`. Кнопки `Створити DOCX/PDF`, `Додати скан`, `Додати підписаний файл`, `Додати файл КЕП`, `Перевірити підпис` (тільки коли доступний справжній перевірник), `Показати оригінал`. Жодне прикріплення не затирає попередню версію.

Сценарій: вибрати сценарій закріплення → обрати 12 реальних пар → побачити всі 12 у додатку → перевірити дату/номер/підставу → зберегти/згенерувати DOCX/PDF → за потреби додати відсканований підписаний примірник → знайти їх разом в одному документі → резервувати й відновити без змін.

Сценарій: обрати довгу програму інструктажу (30+ сторінок) → скоригувати розділ і зберегти нову редакцію шаблону → створити конкретний комплект з темою/датою/учасниками → отримати DOCX/PDF + лист ознайомлення → пізніше добровільно додати скан журналу або електронно підписаний файл → зберегти стару й нову редакції та видимий статус перевірки підпису.

## 9. Поетапне впровадження (не частина r8)

1. **Схема/контракт та поведінкові тести** на вигаданих даних; інвентаризація старих сховищ.
2. **Бібліотека користувача**: template CRUD + редакції + імпорт JSON package v1 + доступність між оновленнями.
3. **Редактор великих текстів**: структурні розділи, навігація, DOCX import с preview втрат, довгі таблиці, формування DOCX/PDF.
4. **Архів документів**: уніфікований каталог + immutable вкладення, скани, зв'язки й пошук; адаптер старих документів.
5. **Електронні підписи**: безпечне збереження оригіналу/відокремленого підпису, окрема інтеграція справжньої валідації, чесні статуси.
6. **Backup/restore**: повна перевірка 2 БД + library + index + all assets, cross-platform.
7. Повний regression на Windows/Win7 Python 3.8/macOS Intel+ARM; після тестового випуску й рішення власника — stable.

Заборонено без рішення власника змінювати stable v10.16-r8 або перезаписувати історичні теги. Наступний кодовий випуск — нова тестова ревізія, не reuse виданих номерів.
