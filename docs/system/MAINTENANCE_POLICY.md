# Taxo 9.0 — правила супроводу після стабілізації

## Поточний режим

Після випуску **Taxo 9.0** система переходить у режим реальної експлуатації та накопичення даних.

Пріоритет на цьому етапі:

1. стабільність;
2. збереження даних;
3. відтворюваність помилок;
4. виправлення дефектів, знайдених у реальній роботі;
5. лише після цього — нові функції.

## Що вважається зміною, яку можна робити одразу

Без окремого великого функціонального етапу допускаються:

- виправлення падінь і помилок даних;
- виправлення помилкових розрахунків;
- виправлення друку/відображення, якщо дані не змінюються;
- уточнення текстів, інструкцій і повідомлень;
- покращення сумісності з Windows/macOS;
- додаткові тести, що фіксують уже очікувану поведінку.

## Що потребує окремого погодження

Перед реалізацією окремо фіксуються:

- нова сутність у БД;
- зміна значення існуючих полів;
- новий алгоритм автоматичного розпізнавання тахокарт;
- автоматичне перенесення факту у план;
- зміна правил нумерації офіційних документів;
- зміна логіки видалення/архівування історії;
- масове перерахування старих даних;
- новий нормативний алгоритм контролю.

## Процес виправлення дефекту

Для кожної проблеми бажано зафіксувати:

- версію (`9.0`, майбутню `9.x` тощо);
- ОС;
- робочий розділ;
- вхідні умови;
- кроки відтворення;
- очікуваний результат;
- фактичний результат;
- чи зачіпає помилка дані в БД;
- чи є безпечний обхідний шлях.

Після цього:

1. Створюється окрема гілка.
2. Додається тест, який відтворює дефект, якщо це можливо.
3. Вноситься мінімальне виправлення.
4. Запускаються наявні регресійні тести.
5. Перевіряється робота на Windows/macOS, якщо зміна платформозалежна.
6. Формується candidate/patch-реліз.
7. Лише після перевірки зміна потрапляє в stable.

## Версіонування після 9.0

Рекомендована схема:

- `9.0.x` — термінові/локальні виправлення без зміни функціональної моделі;
- `9.1`, `9.2` — невеликі експлуатаційні покращення, підтверджені практикою;
- `10.0` — лише для суттєвого нового етапу або зміни моделі системи.

Якщо під час реальної експлуатації виявиться, що зручніше зберегти поточну внутрішню схему candidate `rN`, її можна застосовувати до PR/тестових збірок, але stable-релізи бажано мати просту зрозумілу нумерацію.

## Інваріанти, які не можна ламати без окремого рішення

- БД і персональні дані не включаються в GitHub Release.
- План і факт не зливаються автоматично.
- Тахографічний факт не переписує планові `worklog/work_segments`.
- Історичні документи не видаляються без контрольованого механізму.
- Номер уже випущеної шляхівки не повертається в пул через звичайне анулювання.
- Відсутність даних не повинна маскуватися під відпочинок у 60-денному реєстрі.
- Робоче сховище має залишатися переносимим між версіями без ручного перепакування бази.

## Експлуатаційний журнал

Під час перших місяців роботи корисно вести простий журнал спостережень:

- дата;
- користувач/роль;
- розділ;
- що робили;
- проблема/незручність;
- критичність;
- чи впливає на дані;
- запропоноване рішення.

Не кожне побажання треба одразу реалізовувати. Після накопичення реальної статистики легше відрізнити системну проблему від одиничного сценарію.
