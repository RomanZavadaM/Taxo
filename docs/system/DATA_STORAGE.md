# Taxo 9.0 — дані, сховище та резервування

## Розділення програми і даних

Taxo встановлюється/розпаковується окремо від робочих даних. Оновлення програми не повинно вимагати ручного перенесення БД між папками версій.

## Робочий корінь

За замовчуванням використовується `Documents/DriverWorktime`, якщо користувач не вибрав інше сховище.

Через `Файл → Робоче сховище…` можна підключити локальний, мережевий або синхронізований каталог.

## Що входить у робочі дані

У робочому сховищі зберігаються:

- основна SQLite БД з підприємством, працівниками, водіями, транспортом, маршрутами, графіками, табелями, шляхівками, бланками та історією;
- окрема тахографічна SQLite БД;
- скани тахокарт;
- сформовані PDF/DOCX/JPG;
- шляхові листи;
- архіви попередніх/вилучених редакцій бланків;
- резервні копії;
- журнали помилок.

Конкретні внутрішні шляхи можуть змінюватися між версіями, тому адміністратору слід резервувати **весь робочий корінь**.

## Відносні посилання на файли

Файли, що належать робочому сховищу, можуть зберігатися в БД як відносні `workspace://` адреси. Це дозволяє одному й тому самому набору даних працювати на різних комп’ютерах, де синхронізована папка має різний локальний шлях.

## Блокування

Сховище має механізм lock/heartbeat. Його мета — не допустити одночасний запис двома копіями Taxo.

Блокування не є системою багатокористувацьких транзакцій. Робоча модель v9.0 — **послідовний доступ**.

## SQLite

БД не повинна копіюватися вручну під час активного запису. Для перенесення використовується штатний механізм, який застосовує SQLite backup і контроль цілісності.

Після критичних операцій або перед міграціями створюються резервні копії.

## Рекомендована політика резервування

Мінімальна практична політика підприємства:

- автоматична щоденна копія робочого сховища;
- щонайменше одна копія на іншому носії/сервері;
- окрема контрольна копія перед оновленням програми;
- регулярна перевірка відновлення, а не лише факту наявності ZIP/папки;
- збереження копій відповідно до внутрішньої політики підприємства та вимог до документів.

## GitHub і персональні дані

Репозиторій та GitHub Release не повинні містити:

- `.db`;
- `.sqlite`;
- `.sqlite3`;
- реальні скани тахокарт;
- реальні документи працівників;
- робочі резервні копії.

CI релізу перевіряє пакети на відсутність SQLite-файлів.

## Оновлення до нової версії

Правильна послідовність:

1. Закрити всі копії Taxo.
2. Дочекатися синхронізації, якщо вона використовується.
3. Зробити повну резервну копію робочого кореня.
4. Оновити програму.
5. Відкрити існуюче сховище.
6. Перевірити `quick_check`/штатне відкриття, ключові довідники й один тестовий звіт.
7. Не видаляти попередню резервну копію одразу після першого успішного запуску.

## Відновлення

Перед відновленням старої БД необхідно врахувати, що після дати резервної копії могли бути створені нові шляхівки, бланки, номери документів та інші записи. Відновлення «одного файла поверх поточного» може створити логічну втрату історії навіть якщо SQLite відкривається без помилки.

Тому відновлення слід виконувати як контрольовану операцію з копією всього сховища.
